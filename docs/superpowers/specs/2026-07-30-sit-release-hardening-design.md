# Test/SIT 发布候选规范化设计

## 1. 目标

把当前 `cfpd/test` 本地缓存基线 `c686b11` 收口成一份可重复检查、可识别版本、容易交接的 Test/SIT 发布候选。

本轮解决的是“发布前能否提前发现暗病、能否证明部署的是哪一版、后续开发能否按统一标准接手”，不是正式生产上线，也不连接公司外部资源。

## 2. 已确认边界

- 只在本地分支实施和提交，不推送 `cfpd/test`，不触发 Libra。
- 保留现有 Mock 数据、Mock 文件和相关页面，本轮不清理、不替换、不隐藏。
- Test/SIT 的简历 AI 继续关闭，保留原件后走人工补录。
- 不清理、不覆盖现有本地数据库和附件；自动验证优先使用临时数据库。
- 不接公司账号、正式数据库、域名、证书、外部通知、LLM Key 或真实候选人数据。
- 不做微服务拆分、框架替换、大规模重构或纯视觉翻新。

## 3. 第一性原理

一份可信的 Test/SIT 发布候选必须同时满足五个条件：

1. **能识别**：能准确说出前端、后端、构建渠道和预期数据库版本。
2. **能重复**：换一台机器或换一个接手者，也能按同一条命令得到同一类结果。
3. **能拦错**：高危依赖、错误配置、迁移分叉、敏感文件和构建失败不能被当作可发布。
4. **能补救**：已关闭能力和常见失败必须告诉用户下一步，不能出现假成功或无解释空白。
5. **能交接**：当前目录、命令、版本和限制只有一套真源，不依赖口头记忆。

## 4. 设计内容

### 4.1 JavaScript 依赖安全收口

- 升级 React Router 到当前最新稳定版本，并保持现有 `BrowserRouter` 路由行为。若 npm 在上游尚无修复版本时仍报告仅影响未启用 RSC 模式的公告，只允许按公告编号建立单条、有代码证据的例外；任何新公告仍必须失败。
- 升级或重解析 ESLint 工具链中的高危间接依赖。
- 不直接使用不可审查的 `npm audit fix --force`；任何大版本变化都必须经过测试、类型检查、Lint 和生产构建。
- 发布门禁要求开发依赖没有未处理高危结果；线上依赖只允许机器可核对的 `GHSA-qwww-vcr4-c8h2` 单条例外，因为当前应用只使用 `BrowserRouter`，没有 RSC 路由、Server Action 或服务端 Router handler。例外必须在扫描输出中明确显示，不能静默忽略；出现任何其他高危公告都必须失败。

### 4.2 Python 依赖安全收口

- 提供仓库内固定入口运行 Python 依赖审计，扫描 `backend/requirements.txt`。
- 审计工具版本固定，避免不同机器得到不可比较的行为。
- 有安全升级时优先做最小兼容升级并运行后端全量测试。
- 暂无修复版本时，发布检查必须明确列出包名、漏洞和暂缓理由，不把失败伪装成成功。

### 4.3 Test/SIT 配置自检

- 在现有生产自检之外增加 Test/SIT 专用模式或独立只读入口。
- 校验占位值、弱密钥、数据库类型、持久附件/备份目录、公开注册、安全头、限流、AI 开关和角色默认值。
- 校验前后端角色映射格式可解析；不要求本轮填入真实公司工号。
- 示例模板可以保留占位符，但把模板当作真实部署配置运行时必须失败。
- 自检不得打印数据库密码、JWT 密钥、Cookie 加密密钥或其他敏感值。

### 4.4 前后端版本身份证

- 构建时注入统一的短提交号、构建渠道和构建时间；未注入时使用明确的 `local/unknown`，不得伪造提交号。
- 后端在只读信息端点返回服务名、版本、渠道和预期 Alembic head，不返回环境秘密。
- 前端在登录页低干扰显示 Test/RC 和短版本号，并把版本写入构建产物。
- 前后端使用同一批次信息时才允许发布检查通过。
- 健康检查继续只代表进程存活；版本信息不得冒充数据库已经迁移成功。

### 4.5 统一发布门禁

- 新增一条仓库级只读命令，顺序执行后端测试、前端测试、类型检查、Lint、构建、安全审计、Alembic head、Git 格式和敏感文件检查。
- 各步骤显示清楚的中文成功/失败结果；任一硬门槛失败时整体返回失败。
- 对耗时步骤显示当前阶段，避免用户误以为命令卡死。
- 门禁不自动修改依赖、不自动迁移数据库、不清理数据、不提交或推送代码。
- 输出一份可保存的本次发布候选摘要，包括提交号、迁移版本、检查结果和已知限制。

### 4.6 异常补救复核

- 只复核本轮 Test 试用直接相关的现有路径：简历 AI 关闭后的人工补录、接口失败与重试、重复提交、登录失效和明确空态。
- 已有行为符合要求时只补测试或记录，不为了“顺便优化”重写页面。
- 只修验证中能够稳定复现的阻断问题；新的产品需求另开范围。

### 4.7 文档真源同步

- 把当前主前端统一写为 `readdy-frontend/`。
- 把当前 Alembic head 统一写为 `20260730_13`。
- 更新真实测试命令、Test/SIT AI 关闭口径和版本核对方式。
- 明确 Mock 数据本轮保留，不能把 Test 试用结果描述成全站真实数据生产验证。
- 只修改当前真源文档；历史计划保留为历史，不做机械改写。

## 5. 数据流与失败处理

发布检查从 Git HEAD 读取版本，分别传给前端和后端构建；代码内只消费非敏感构建元数据。配置自检只读取配置并输出脱敏结论。安全审计、测试和构建都使用原工具的退出码，统一门禁只负责编排，不吞掉失败。

任何步骤失败时：

- 显示失败阶段和下一条可执行建议。
- 保留原始退出码和必要摘要。
- 不自动执行 `--force`、数据库迁移、文件删除、Git 提交或远端发布。

## 6. 验收标准

本轮完成必须同时满足：

- 后端 `backend/tests` 与 `base_agent/tests` 全量通过。
- 前端 `readdy-frontend/tests/*.test.mjs` 全量通过。
- 前端类型检查、Lint 和正式构建通过。
- JavaScript 开发依赖无高危审计结果；线上依赖除明确且机器校验的 `GHSA-qwww-vcr4-c8h2` RSC 非适用例外外，不得有其他高危结果。
- Python 依赖审计可重复执行，结果已处理或明确记录。
- Alembic 只有一个 head，且为 `20260730_13`。
- Test/SIT 自检能通过安全样例测试，并稳定拒绝占位值和危险配置。
- 前后端版本信息可测试、无敏感字段、能区分本地和 RC 构建。
- 统一门禁在全部成功时退出 0，在任一硬门槛失败时非 0。
- `git diff --check` 通过，工作区没有误纳入运行数据或构建产物。
- README、RUNNING、DEPLOYMENT 和当前上线清单不再使用错误目录或旧迁移版本。

## 7. 完成后的用户效果

- 发布前运行一条命令，就能提前发现依赖、测试、构建、配置、迁移和敏感文件问题，减少“表面正常、试用几天后才爆雷”的暗病。
- 测试站出现问题时，可以立即判断前端、后端和预期数据库是否属于同一版，减少排查“到底发布了什么”的时间。
- 后续开发者只需看当前真源文档并运行统一门禁，不必翻历史记录或依赖口头经验。
- 每次后续修改都会复用同一套标准，降低增加新功能时破坏旧功能的概率。
- 当前交付会成为一份规范的本地 Test/SIT 发布候选，但仍不代表已经部署到 SIT，也不代表允许使用真实候选人数据。

## 8. 明确不解决的问题

- 不处理或清理 Mock 数据。
- 不验证公司真实工号映射、统一登录和权限数据范围。
- 不验证公司 MySQL、附件持久卷、备份恢复或 K8S 资源。
- 不处理真实简历发送给外部模型的合规结论。
- 不执行远端推送、Libra 构建、SIT 发布或生产发布。
