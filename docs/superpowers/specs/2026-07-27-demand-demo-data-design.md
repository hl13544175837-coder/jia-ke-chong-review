# 招聘需求全状态演示数据设计

## 目标

为本地演示环境补充一组真实写入数据库的招聘需求，让招聘专员能在“招聘需求”页面发现并实际操作每个状态入口。演示数据只服务本地讲解，不替代生产数据，不在前端写死假卡片。

## 演示场景

使用固定需求编号和直白名称，覆盖以下状态：

1. `演示需求-待审核`：由业务角色提交，审核状态为待审核；招聘专员打开详情后可选择“通过”或“不通过”。
2. `演示需求-招聘中`：已审核且招聘中；可直接打开“选候选人”，查看阶段人数，并使用关闭操作。
3. `演示需求-已完成`：正常完成招聘；可查看关联候选人并恢复招聘。
4. `演示需求-已暂停`：临时停止招聘，显示在“已停止”；可恢复招聘。
5. `演示需求-已关闭`：已结束招聘，显示在“已停止”；可查看关联候选人并恢复招聘。

每条数据包含岗位、JD、部门、城市、招聘负责人、用人负责人、HC、期望完成日期、优先级和状态说明，避免用户必须猜测数据用途。

## 实现方式

新增独立本地脚本 `backend/scripts/add_demand_demo_data.py`，复用现有 Flask 应用、模型和本地数据库配置。脚本按固定 `request_no` 查找并更新数据，因此可重复运行，不会不断新增重复需求。

脚本优先复用当前组织内的招聘专员、面试官和职位模板；缺少必要账号或职位模板时明确失败并说明原因，不静默制造无效数据。只操作当前配置指向的本地 SQLite 演示数据库；若检测到非 SQLite 数据库则拒绝执行，防止误写公司试点或生产环境。

## 数据关系

待审核需求必须带真实 `submitted_at`，确保详情中出现审核按钮。招聘中、已完成和已关闭场景应关联少量已有候选人流程记录，使“选候选人”“查看候选人”和阶段人数不是空壳；不得破坏候选人已有需求归属。

## 测试与验收

- 增加脚本测试，验证五个固定需求编号、对应状态、待审核提交时间、重复运行不增量，以及非 SQLite 防误写。
- 运行后用招聘专员账号逐项打开“待审核、招聘中、已完成、已停止”。
- 实际验证“通过/不通过”入口、“选候选人”、查看候选人、关闭和恢复入口可发现。
- 跑后端相关测试、前端全量可运行测试、lint、类型检查和正式构建。

## 非目标

- 不接公司 OA、企业微信或远端数据库。
- 不改变招聘需求状态定义、按钮逻辑或现有技术栈。
- 不伪造第三方通知成功，不自动执行会改变演示状态的最终确认操作；只验证入口和表单可用。
