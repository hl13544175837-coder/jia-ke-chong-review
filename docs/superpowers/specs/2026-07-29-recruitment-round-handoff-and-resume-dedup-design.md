# 二面信息承接、重复简历拦截与界面收口设计

## 目标

在不改变现有 React + Flask + SQLAlchemy 模块化单体路线的前提下，完成以下试点闭环：

1. 招聘专员安排一面，一面面试官提交评价后，再安排不同账号负责二面。
2. 二面面试官能只读查看一面的安排与评价，但不能修改一面数据；无关面试官不能查看。
3. 已存在的相同简历再次导入时不创建第二份候选人档案，并明确提示“系统中已存在重复简历”。
4. 面试官、业务筛选人和招聘专员继续复用同一份候选人招聘历程组件，用清晰节点表达每轮结果。
5. 增加第二个面试官试用账号，统一面试官端相关标题、字体、状态和结果组件。

## 架构边界

- 权限 owner 仍是后端 RBAC、assignment 和 Demand 范围校验；前端不自行推断权限。
- 面试轮次仍由 `InterviewAssignment.round_sequence` 表达，主流程仍只有 `interview`，不新增“一面/二面”主阶段。
- 重复简历检测仍属于现有 `/api/resume/upload` 上传链路，不新增服务或队列。
- 候选人历程继续由 `/api/candidates/<id>/journey?demand_id=<id>` 提供，不增加第二份历程接口。
- 前端继续使用 Readdy React 应用和现有 Tailwind 设计变量，只增强共用组件。

## 二面承接一面信息

招聘专员先创建第一轮 assignment；第一轮面试发生并由招聘专员确认后，一面面试官提交评价。招聘专员随后为同一 Demand、同一候选人创建 `round_sequence=2` 的 assignment，并指定第二个面试官账号。

二面面试官进入自己的第二轮任务时：

- assignment 列表只返回分配给自己的任务；
- 候选人 journey 按当前 Demand 返回第一轮和第二轮安排；
- 第一轮评价作为只读历史显示；
- 当前账号只能创建或修改自己第二轮 assignment 对应的评价；
- 无 assignment、无业务筛选任务的其他面试官访问 journey 返回 403。

## 重复简历判断

使用两级强判断，避免仅凭姓名误判：

1. 原始文件 SHA-256 完全一致：直接判定为重复，无需再次调用解析器。
2. 解析后的完整手机号或邮箱与当前组织的活动候选人一致：判定为重复，删除本次临时候选人和临时文件，不自动覆盖已有档案。

`Candidate` 增加可空 `resume_sha256`，并增加 `(org_id, resume_sha256)` 普通索引。历史行允许为空，避免破坏性回填。上传返回结果增加：

- `status: "duplicate"`
- `reason: "导入失败：系统中已存在重复简历"`
- `existing_candidate_id`
- `existing_candidate_name`
- `match_basis: "文件内容一致" | "手机号一致" | "邮箱一致"`

批量上传允许部分成功。重复文件不计入成功，不自动覆盖、不自动进入 Demand 流程。

## 界面与组件收口

- `CandidateJourneySummary` 继续作为招聘专员、业务筛选和面试官共用历程组件。
- 每轮面试显示明确的完成、待反馈、未通过图标和文字；历史评价保持只读。
- 面试官工作台、导航和筛选页统一使用当前已确认的“待面试官筛选”名称。
- 简历上传结果分别统计成功、重复、其他失败；重复项显示已有候选人和匹配依据。
- 不启用旧 mock `CandidateDetailDrawer`，避免重新引入第二套候选人详情事实。

## 测试与验收

后端自动化必须真实走通：

1. HR 创建一面；一面面试官读取、确认后提交通过评价。
2. HR 创建二面并指定第二个账号。
3. 二面账号读取自己的 assignment 和 journey，看到一面评价。
4. 二面账号不能修改一面评价；无关账号访问失败。
5. 同一文件二次上传返回 duplicate，解析器不再次运行，数据库只有一名候选人。
6. 不同文件但完整手机号或邮箱一致时返回 duplicate，数据库仍只有一名候选人。

前端必须通过类型检查、lint、构建、相关契约测试，并检查上传结果和候选人历程的用户可见文案。

## 风险控制

- 权限风险：所有读取和写入继续由后端 assignment 校验，增加正向和负向测试。
- 误判风险：不使用姓名作为重复判断依据；仅使用文件哈希、完整手机号或完整邮箱。
- 数据风险：新增字段为可空加性迁移，不修改既有候选人、面试或流程数据。
- 页面风险：只改共享组件和当前入口，不进行全站重写。
