# MySQL 试点招聘闭环接入设计

> 确认日期：2026-07-24
>
> 适用项目：`zhipin-readdy-resume-20260724/app`
>
> 适用入口：`readdy-frontend`，本地端口 `5190`
>
> 状态：产品方案已确认；只在公司测试 MySQL 和本隔离项目内实施，不部署、不推送。

## 1. 目标

把当前 5190 的演示业务数据接到公司测试 MySQL，形成几名内部用户能够真实跑通的最短招聘闭环：

`业务提交招聘需求 -> HR 审核 -> HR 筛选 -> 业务筛选 -> 一面 -> 二面 -> Offer -> 入职`

本轮优先保证真实保存、刷新不丢、角色看到正确待办和研发可继续接手，不建设复杂审批、多级组织治理或额外安全平台。

## 2. 本轮边界

### 包含

- 连接用户指定的测试 MySQL，连接信息只由本地运行环境注入。
- 用现有 7 个试点账号和 4 类技术角色完成业务闭环。
- 业务负责人按现有 `Job` 模板填写并提交招聘需求。
- 招聘专员或招聘主管审核需求，通过或不通过。
- 真实简历上传、候选人详情、原版简历预览和下载。
- HR 筛选后推送给指定业务负责人。
- 业务负责人提交通过、不合适或需要 HR 补充信息。
- 一面和二面分别安排、填写及修改评价。
- HR 根据业务筛选和面试反馈手工推进，不做自动淘汰或自动进入下一阶段。
- 必要的数据库结构补齐、备份、回滚和审计记录。

### 不包含

- 不连接生产数据库，不部署到 SIT 或生产，不推送 Git。
- 不接 AI 助手、BOSS 自动化、KPI 标准、外部日历、邮件或短信。
- 不建设新的微服务、消息队列、复杂多组织审批或精细到字段级的权限系统。
- 不删除、匿名化或批量改写测试库现有岗位、候选人和旧面试记录。

## 3. 已确认的数据库现状

对用户提供的测试 MySQL 已完成只读检查：

- MySQL 版本为 8.0.32，当前库可通过 Python MySQL 驱动连接。
- 当前共有 7 个用户、4 个岗位模板、10 位候选人和 3 条旧面试记录。
- `recruitment_demands`、`candidate_demand_flows`、`interview_assignments`、`interview_feedback`、`offer_records` 当前均无新流程业务记录。
- `alembic_version` 登记为 `20260710_01`，但数据库中已经存在部分后续迁移的表和字段。
- 数据库缺少当前代码依赖的部分字段、索引和表，例如需求默认面试官、完整 Offer 生命周期字段及 KPI 表。

因此不能直接执行全部历史迁移，也不能假定数据库已经与 ORM 一致。实施时必须先做结构对账，再执行只增不删的兼容修复。

## 4. 总体架构

```text
Tabbit / 5190 React 前端
        |
        | HTTP /api，Bearer Token
        v
本隔离项目 Flask 后端
        |
        | SQLAlchemy + PyMySQL
        v
公司测试 MySQL

原版简历文件
        |
        v
本隔离项目的持久上传目录，数据库只保存文件引用
```

浏览器不能直接连接 MySQL。5190 只调用 Flask API；Flask 负责登录身份、最小角色校验、业务状态校验、审计和数据库事务。

测试 MySQL 密码不得写进源码、文档、启动脚本、日志或 Git。运行时通过本机未跟踪的环境文件或终端环境变量注入。SQLite 启动方式继续保留，新增独立的 MySQL 试点启动入口，避免误把普通本地演示连接到公司测试库。

## 5. 角色与最小权限

沿用现有技术角色，不新增角色枚举：

| 技术角色 | 产品职责 |
|---|---|
| `interviewer` | 业务负责人 / 面试官：提交需求、处理分配给自己的业务筛选和面试任务 |
| `recruiter` | 招聘专员：审核需求、HR 筛选、推送业务、安排面试和推进流程 |
| `manager` | 招聘主管：拥有招聘专员能力，并可查看团队范围 |
| `admin` | 系统管理员：管理账号和排障，不代替 HR 日常推进 |

试点只有一个组织和少量账号，不增加部门级数据墙。仍保留三条最低限度规则：必须登录；面试官只能处理指派给自己的任务；只有 HR、主管或管理员能推进招聘流程。这样既不增加使用门槛，也避免不同业务负责人互相修改任务。

## 6. 招聘需求审核

### 6.1 模板与提交

现有 `Job` 继续作为可复用岗位/JD 模板。业务负责人选择模板后填写部门、城市、HC、期望到岗时间、优先级、完整 JD 和面试关注点，提交为一条 `RecruitmentDemand`。

业务负责人创建的需求固定进入：

- `status = pending`：尚未正式开始招聘。
- `approval_status = pending`：等待 HR 审核。
- `created_by`：当前业务账号。
- `default_interviewer_id`：默认当前业务账号，也允许明确选择其他业务负责人。

### 6.2 审核结果

招聘专员和招聘主管都可审核：

- 通过：`approval_status = approved`，`status = active`，记录审核人和时间。
- 不通过：`approval_status = rejected`，`status` 保持 `pending`，不通过原因必填。
- 业务负责人修改被拒需求并重新提交后，`approval_status` 回到 `pending`；历史拒绝原因保存在审计事件中。
- 需求一旦通过，业务负责人不再直接修改核心招聘字段，后续变更由 HR 处理。

`RecruitmentDemand` 增加以下审核事实：

- `approval_status`：`pending`、`approved`、`rejected`。
- `submitted_at`：最近一次提交时间。
- `reviewed_by`：最近一次审核人。
- `reviewed_at`：最近一次审核时间。
- `review_reason`：最近一次不通过原因，通过时为空。

## 7. HR 筛选与业务筛选

候选人进入某条 Demand 后，HR 完成初筛并选择业务负责人。推送动作创建一条独立的 `BusinessReviewTask`，不只依赖看板阶段推断待办。

`BusinessReviewTask` 保存：

- 组织、Demand、候选人、指派业务负责人。
- 状态：`pending`、`approved`、`rejected`、`needs_info`。
- HR 筛选备注、业务备注、处理截止时间。
- 创建人、提交人、创建时间、提交时间和更新时间。
- 同一候选人、同一 Demand 同一时间最多一条待处理任务，防止连点重复推送。

业务筛选固定三个结果：

| 结果 | 数据状态 | 后续动作 |
|---|---|---|
| 通过，进入一面 | `approved` | 返回 HR，等待 HR 安排一面 |
| 不合适 | `rejected` | 原因必填，返回 HR 确认是否淘汰 |
| 需要 HR 补充信息 | `needs_info` | 原因必填，HR 补充后可再次推送 |

业务筛选提交后只保存结论并通知 HR，不自动移动阶段、不自动淘汰、不自动创建面试。

## 8. 简历信息与原版文件

业务筛选和面试详情同时展示：

- 候选人的结构化信息，包括经历、教育、项目和技能。
- 当前招聘需求、完整 JD 和面试关注点。
- 原版简历预览和下载入口。

原版简历通过后端受控文件接口读取。HR、主管、管理员和当前被指派的业务负责人可以访问；其他面试官返回 403。文件不存在时返回明确的 404 和“原版简历文件不存在”，不能显示空白预览。

上传文件保存在本隔离项目对应的持久上传目录。数据库保存相对文件引用，删除本隔离项目时可以按 `docs/ISOLATED_CLEANUP.md` 一并彻底清理，不触碰其他产品目录。

## 9. 面试安排与评价

沿用现有 `InterviewAssignment` 表示一次具体轮次任务，一面和二面各有独立记录。HR 安排后，任务只出现在被指派面试官的“我的面试”。

评价表固定为：

- 满意程度：`satisfied`、`pending`、`unsatisfied`，前端展示“满意 / 待定 / 不满意”。
- 面试备注：自由文本，最多 1000 字。
- 当前候选人、Demand、轮次、任务和面试官。

满意程度保存在 `InterviewFeedback.evaluation_json.satisfaction`，备注保存在 `note`。同一 assignment 只有一条当前反馈；原面试官可修改自己的反馈，主管和管理员可协助修正。每次新增或修改都写入审计事件，包含修改人、时间和修改前后的核心值。

反馈修改不设置额外审批，也不因 HR 已经推进而锁死。界面明确显示最后修改人和时间。面试反馈不自动推进流程，仍由 HR 决定进入二面、Offer 或淘汰。

## 10. API 边界

在现有 Flask API 风格内补齐以下能力：

- `GET /api/jobs`：业务负责人读取岗位模板。
- `POST /api/demands`：业务负责人提交待审核需求；HR 仍可创建需求。
- `GET /api/demands`、`GET /api/demands/<id>`：按角色返回本人或团队可见需求。
- `POST /api/demands/<id>/approve`：HR 或主管通过需求。
- `POST /api/demands/<id>/reject`：HR 或主管不通过，原因必填。
- `POST /api/demands/<id>/resubmit`：原创建人修改后重新提交。
- `POST /api/business-reviews`：HR 推送业务筛选。
- `GET /api/business-reviews/mine`：业务负责人读取本人任务。
- `POST /api/business-reviews/<id>/decision`：提交三种固定结论。
- `GET /api/candidates/<id>/resume-file`：受控预览或下载原版简历。
- 复用现有 interview assignment 和 feedback 路径，补齐简单评价和修改语义。

所有写接口继续使用现有幂等键或唯一约束防重复提交。401 表示登录失效，403 表示角色或任务不属于本人，404 表示业务记录或文件不存在，409 表示状态已经变化或重复提交，400 表示字段缺失。

## 11. 数据库兼容与迁移

### 11.1 结构对账

新增一个只读结构审计脚本，逐项比较 `information_schema` 与当前代码依赖，输出：

- 已存在且定义一致。
- 缺失、可以安全新增。
- 已存在但定义冲突，必须停止人工确认。

审计报告不能包含密码、连接串或候选人个人信息。

### 11.2 兼容修复

在第一次写测试库前生成可恢复备份。随后执行确定性的兼容迁移：

- 只新增缺失的列、索引、外键和表。
- 不删除、不重命名、不清空任何现有对象。
- 已存在对象先校验定义，一致则跳过，不一致则停止。
- 先补齐历史迁移 02 至 07 实际缺失部分，再新增本轮需求审核和业务筛选迁移。
- 只有结构核对完全通过后，才更新 Alembic 版本登记。

当前新流程表为空，因此允许补字段和约束；旧岗位、候选人及面试记录原样保留。若备份失败、发现冲突结构或待变更表在执行前出现新数据，本次写入立即停止。

### 11.3 回滚

代码回滚只需停止 MySQL 试点启动入口并重新使用原 SQLite 启动方式。数据库回滚优先恢复执行前备份；本轮迁移不提供自动删除新增列的在线降级，避免误删后续产生的试点数据。

### 11.4 删除边界

接入共享测试 MySQL 后，“删除本地项目”和“删除数据库数据”是两件事：

- 本地代码、进程、日志和上传文件仍可按 `docs/ISOLATED_CLEANUP.md` 清理干净。
- 同事实际录入的试点业务数据默认保留，不能因为删除本地目录而自动删除。
- 自动化验收创建的临时需求、候选人和任务必须使用明确的验收标识，并把记录 ID 写入本隔离运行目录的清理清单。
- 提供只读预览和显式确认两步的验收数据清理脚本；脚本只处理清单中的临时记录，发现清单外引用立即停止。
- 本轮新增的数据库字段和表属于共享测试库结构，不跟随本地目录自动删除。以后如需移除，必须单独备份并取得明确的数据库变更指令。

因此，用户以后只说“删除本地版本”时，不修改共享 MySQL；只有明确要求“同时清理本次验收临时数据”时，才执行带预览和记录核对的数据库清理。

## 12. 前端改造

5190 继续保留现有视觉和五套角色界面，只替换业务事实来源：

- 招聘需求页增加“待审核 / 已通过 / 未通过”状态和审核按钮。
- 业务负责人招聘需求页使用真实模板和提交接口。
- “待业务筛选”改为真实任务列表，详情展示 JD、结构化简历和原版文件。
- 业务筛选弹窗只保留三个结论和备注。
- “我的面试”读取真实 assignment，评价弹窗改为满意程度和备注。
- 数据为空时显示真实空态；接口失败时显示失败和重试，不能用 mock 的 0 或固定候选人代替。
- AI 助手、BOSS 自动化和 KPI 标准继续从试点导航隐藏。

公共 API 层统一处理 Bearer Token、请求 ID、JSON 错误、401 退出、403 提示和 409 刷新，页面不各自拼接连接地址。

## 13. 测试与验收

实施采用测试先行，每项行为先写失败测试，再写最小实现。测试分四层：

1. 后端单元和 API 测试：角色权限、需求审核、筛选三结论、评价修改、文件访问和幂等冲突。
2. 数据库结构测试：空库迁移、当前测试库只读审计、重复执行兼容迁移无重复 DDL。
3. 前端契约和组件测试：状态文字、按钮权限、必填原因、真实 API 调用及错误态。
4. Tabbit 端到端验收：使用不同角色完成完整最短流程，刷新页面确认数据仍在。

本轮完成标准：

- 业务账号提交需求，HR 能通过或不通过；拒绝原因可见并可重新提交。
- HR 上传一份专用测试简历，刷新后候选人仍存在。
- HR 推送业务筛选后，只有指定业务账号看到任务。
- 结构化简历和原版文件均可查看，原版文件可下载。
- 三种业务结论真实保存，必填原因规则正确。
- 一面、二面评价分别保存，修改后可见最后修改信息和审计记录。
- 业务筛选和面试反馈都不会自动推进，HR 可以继续手工推进。
- 重复点击不会生成重复需求、任务或反馈。
- 现有 4 个岗位、10 位候选人和 3 条旧面试记录未被删除或批量改写。
- 后端测试、前端测试、类型检查、lint、构建和 5190 Tabbit 冒烟均通过。

## 14. 实施分片与顺序

为降低一次改动范围，本设计拆成四个可以独立验收的实施分片；每个分片完成测试后再进入下一个：

1. 数据底座：固化结构审计、备份前置检查、只增不删的兼容迁移、MySQL 试点启动方式和公共 API 层。
2. 需求审核：实现业务提交需求、HR 通过/不通过、重新提交和状态界面。
3. 候选人与业务筛选：实现简历上传、原版文件、候选人详情、业务筛选任务和三种结论。
4. 面试闭环：实现一面、二面任务、可修改评价、HR 手工推进、多角色 Tabbit 验收和交接记录。
