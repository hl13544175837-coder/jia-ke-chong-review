# 招聘演示流程顺滑化设计

> 确认日期：2026-07-26
>
> 适用入口：`readdy-frontend`，本地端口 `5190`
>
> 状态：用户已确认按产品走查结论实施；Mock 数据本身不属于本轮问题。

## 1. 目标

让招聘专员、业务负责人 / 面试官在 5190 中顺畅完成这条演示链路：

`需求内选人或导入简历 -> 加入当前需求 -> 推送业务筛选 -> 业务负责人收到待办并处理 -> 招聘专员收到结果并安排面试 -> 面试官收到真实面试任务并反馈`

本轮只解决操作上下文丢失、跨角色待办不可见、下一步不清楚和面试安排未接通的问题。现有演示数据可继续保留，但用户刚刚产生的真实操作必须在下一角色页面出现。

## 2. 用户可见规则

### 2.1 需求内选人

- 招聘需求列表的“选候选人”在当前页面打开右侧工作区，不再强制跳到全局简历库。
- 工作区固定显示当前需求名称、编号和城市，并按该需求计算候选人匹配度。
- 用户可以搜索、勾选候选人并直接加入当前需求。
- 用户可以在工作区拖入 PDF、DOCX、图片或 ZIP；上传时自动关联当前需求，无需再次选择。
- 已经在当前需求、其他进行中需求或已结束流程的候选人必须给出明确状态，不能让用户靠提交后的报错猜测。

### 2.2 从需求查看候选人

- 点击“业务待反馈 / 面试中 / Offer 中”等数字时，可以继续进入完整候选人页，但必须自动带上当前需求和阶段。
- 完整候选人页在需求上下文中显示“某需求 · 候选人”，不再只显示含糊的“简历库”。
- 需求上下文同时预选上传目标，避免简历误入未关联人才库。

### 2.3 业务筛选待办

- 招聘专员推送后，业务负责人工作台和“待业务筛选”页面都读取真实业务筛选任务。
- 工作台保留演示内容，但真实任务必须优先展示并可直接进入处理。
- 顶部通知中心读取真实通知，点击后进入对应任务；已读状态写回后端。
- “推送业务筛选”统一改为“推送业务负责人筛选”，并明确“通过后由招聘专员安排面试”。
- `?task=<id>` 深链必须自动打开对应业务筛选任务。

### 2.4 业务筛选结果

- 业务负责人提交通过、不合适或待补充后，不自动推进候选人流程，继续遵守既有人工确认规则。
- 招聘专员能在候选人页看到最新业务筛选结论和明确下一步：通过后“安排面试”，不合适后“去流程处理”，待补充后“补充并再次推送”。
- 通知深链必须自动定位到对应需求和候选人。

### 2.5 面试安排

- 招聘专员的“面试管理”读取真实 `/interview/management-rows` 数据，不再只修改页面临时状态。
- 安排、调整、确认已完成、催反馈调用真实面试接口。
- 面试官选择来自真实启用账号。
- 安排完成后，任务出现在被指派面试官的“我的面试”。
- 面试官通知链接指向 `/interviewer/interviews`，并带上需求和候选人定位参数。

## 3. 技术边界

- 复用现有 `candidatesApi`、`businessReviewsApi`、`interviewsApi`、`demandsApi` 和 Flask API，不新建平行业务后端。
- 新增小型、单一职责组件，不继续扩大现有 1800 行候选人页面。
- 不重构 Mock 数据体系，不删除旧演示页面和旧组件。
- 不改变“业务筛选和面试反馈不自动推进主流程”的产品规则。
- 不接外部日历、短信、邮件或企业微信。

## 4. 错误处理

- 候选人、评审人、面试官或需求加载失败时，只阻断相关动作，并提供重试。
- 批量加入和批量推送按候选人显示成功与失败结果。
- 上传失败保留用户已选文件和错误原因。
- 面试时间冲突、任务已存在、需求已关闭等后端错误直接使用大白话展示。
- 所有提交按钮在请求期间禁用，防止连点重复。

## 5. 验收标准

1. 从任意招聘中需求点“选候选人”，不跳页，在同页工作区完成搜索、选择和加入。
2. 在该工作区拖入简历后，候选人自动归属当前需求。
3. 从需求阶段数字进入完整候选人页时，需求和阶段已自动筛选。
4. 招聘专员推送业务筛选后，目标业务负责人工作台出现真实待办；点击可直接处理该任务。
5. 业务负责人处理后，招聘专员通知和候选人页显示结论及下一步。
6. 招聘专员安排面试后，目标面试官“我的面试”出现该任务。
7. 页面刷新后上述状态仍存在。
8. 相关后端测试、前端契约测试、类型检查和生产构建全部通过。
