# 业务记录可点击详情与数据下钻设计

## 目标

解决“页面展示了一条业务记录，但用户点不进去、看不到详情或刷新后丢失上下文”的问题。所有改动只使用当前本地 React、Flask 和 SQLite，不增加外部接口，不改变数据库结构。

## 第一性原理

1. 用户看到一条需求、任务、岗位或指标时，首先要能回答“这是什么”。
2. 看到风险或数量后，下一步必须能回答“由哪些记录组成”。
3. 点击详情不等于获得编辑权限；展示范围由角色和现有后端权限决定。
4. 同一个视觉暗示必须对应同一种行为：有悬停反馈就必须可点击。
5. 详情是上下文，不应强迫用户离开当前列表；统一使用右侧抽屉。
6. 可恢复：刷新、前进和后退后，能够恢复当前详情或正确关闭。

## 交互架构

### 共享详情抽屉

新增 `ReadOnlyDetailDrawer`，统一提供：遮罩、标题、说明、关闭按钮、Escape 关闭、滚动区、可选底部操作区。抽屉宽度最大 640px，移动端占满宽度。

### 面试官招聘需求

- 整行是一个语义化按钮，支持鼠标、Enter 和 Space。
- 点击先显示列表中已有内容，再通过现有本地 `GET /api/demands/:id` 补齐完整 JD。
- 详情包括审核状态、需求概况、完整 JD、备注和只读招聘进度。
- 待审核：只显示“等待招聘专员审核”。
- 未通过：显示驳回原因和“修改并重新提交”。
- 已通过：提供“查看待筛选候选人”，跳到该需求对应的面试官筛选列表。
- URL 使用 `?demand=<id>`；关闭时删除该参数。

### 招聘专员工作台

- “待处理事项”整条记录可点击，不再只有小按钮可点。
- “岗位进展”保持数字分别下钻，在岗位名称旁增加明确的“查看需求”提示，避免整行多个动作冲突。

### 招聘进度看板

- `detailCandidate=<id>` 只负责打开流程历史详情。
- `candidate=<id>&target=<stage>` 只负责修改阶段。
- 打开、关闭详情同步 URL；刷新后恢复详情。
- 详情加载失败显示原错误和“重新加载”。

### 管理层招聘进展

- 高风险岗位卡片和岗位清单可打开同一只读详情。
- 详情展示负责人、HC、筛选/面试/Offer、阻塞人数、开放天数、截止日期和阻塞原因。
- 当前页面数据来自本地演示数据，详情只解释现有数据，不产生业务写入。
- URL 使用 `?position=<id>`。

### 数据分析

- 只有能由当前真实分析响应解释的指标可以下钻。
- 本地分析响应为每条需求补充阶段人数、本月入职、本季度入职、Offer 发放和接受数量；全部来自现有 SQLite 事实，不新增表。
- 顶部指标、招聘漏斗、部门进度点击后，使用这些真实需求数据生成明细。
- “招聘成本”仍不可点击，因为当前明确未接入成本数据。
- 下钻只读，不发起新的写接口；详情中的跳转仅进入当前系统已有页面。

## 状态与错误

| 状态 | 用户看到的内容 |
|---|---|
| 首次打开 | 抽屉骨架和“正在加载详情” |
| 加载成功 | 完整只读内容和按角色允许的下一步 |
| 加载失败 | 原错误、人话说明、“重新加载” |
| 记录不存在或无权限 | “该记录不存在或你无权查看”，关闭入口始终可用 |
| 空明细 | “当前条件下暂无组成明细”，保留返回入口 |

## 权限边界

- 面试官只能读取现有后端允许其访问的需求。
- 面试官详情不出现审核、改负责人、Offer、删除或关闭需求按钮。
- 数据分析和管理层详情均为只读。
- 前端隐藏不是权限手段；面试官需求详情继续依赖现有后端 `_authorized_demand`。

## 验收标准

1. 面试官招聘需求整行可点击，能看到完整 JD，刷新后详情仍在。
2. 待审核、未通过、已通过三种需求只出现各自允许的下一步。
3. 工作台待办整条可点击，岗位进展的详情与数字下钻含义清楚。
4. 招聘进度查看详情与修改阶段互不串线。
5. 管理层高风险岗位和清单都能打开同一详情。
6. 真实分析指标、漏斗和部门可以下钻；未接入成本不伪造明细。
7. 所有新增抽屉支持键盘、加载、失败、重试、关闭和焦点样式。
8. 前端全量测试、类型检查、代码规范、构建和后端权限相关测试通过。

## 不在本次范围

- 不把管理层 Mock 数据改造成真实接口。
- 不新增外部通知、外部日历或远端数据源。
- 不修改数据库结构或清理当前本地数据；允许扩展本地只读分析响应。
- 不重构已有候选人、面试、Offer 详情组件。
