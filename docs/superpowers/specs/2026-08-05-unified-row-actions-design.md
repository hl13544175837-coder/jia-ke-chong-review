# 列表操作栏统一整改设计

## 1. 目标

把招聘需求、简历库、面试管理、Offer 和用户管理的列表操作区统一为“一个当前主操作 + 一个更多操作菜单”。主操作负责用户此刻最应该完成的下一步，三个点承载查看、维护、状态管理等次要动作。

本次不是单纯增加按钮数量。每个菜单项必须同时满足：

- 对当前记录状态有意义；
- 当前登录角色有权限；
- 能落到现有真实页面或后端接口；
- 操作成功后刷新真实数据，失败时明确告诉用户原因；
- 不与行内主操作重复。

## 2. 范围

纳入整改：

1. 招聘需求列表；
2. 简历库候选人列表；
3. 面试管理列表；
4. Offer OA 登记列表；
5. 系统设置中的用户管理列表。

不纳入整改：

- 工作台、人才地图、数据看板没有同类操作列，不新增三个点；
- 面试官专属页面继续保持现有角色路径，不借本次需求改版；
- Offer 一期仍然只登记 OA 结果，不增加自动发起 OA、自动发送 Offer、邮件或企业微信能力；
- 不增加需求、候选人、面试、Offer 或成员的物理删除；
- 不修改筛选栏、状态页签、表格业务字段、工作台或分析页面。

## 3. 统一交互规范

### 3.1 行内布局

- 每行最多保留一个有明确下一步的主按钮；没有主任务时可以只显示三个点。
- 三个点按钮固定为 32×32 像素，紧跟主按钮右侧，与现有列表行垂直居中。
- 菜单建议宽度 208 像素，分组之间用细分隔线，不显示无权限、无意义或尚未接入的操作。
- 普通操作使用深灰文字和绿色图标；暂停、取消、关闭、停用账户等高风险操作使用红色提示。
- 菜单靠近视口底部时自动向上展开，靠近右侧时向左对齐，不能被表格或窗口裁切。

### 3.2 操作层级

菜单按以下顺序组织：

1. 查看类：详情、简历、流程、历史；
2. 维护类：编辑、调整、转派；
3. 状态类：暂停、完成、取消、关闭、停用。

状态类操作与其他操作之间必须分隔。需要原因的状态变更继续使用确认弹窗，不能点击后直接生效。

### 3.3 可访问性与关闭行为

- 三个点按钮提供可读名称，例如“打开 Java 开发工程师的更多操作”。
- 按钮声明菜单展开状态；菜单项可以通过键盘聚焦和回车执行。
- 点击菜单外、按 Escape、路由切换或当前记录刷新消失时关闭菜单。
- 菜单点击必须阻止表格整行点击，避免同时打开详情和执行动作。
- 同一时刻最多打开一个行菜单。

## 4. 招聘需求操作规则

### 4.1 主操作

| 当前状态 | 主操作 |
| --- | --- |
| 待审核 | 审核需求；没有审核权限时不显示主按钮 |
| 招聘中且仍有 HC | 选候选人 |
| 招聘中且 HC 已满 | 确认招聘完成 |
| 已暂停 | 恢复招聘 |
| 已完成、已取消、已关闭 | 查看候选人 |

### 4.2 更多操作菜单

通用查看与维护操作：

- 查看需求详情；
- 编辑需求；
- 查看全部候选人；
- 调整优先级；
- 转派负责人，仅招聘主管和管理员显示。

状态操作按当前状态变化：

| 当前状态 | 可显示的状态操作 |
| --- | --- |
| 待审核 | 取消需求 |
| 招聘中且仍有 HC | 暂停招聘、标记招聘完成、取消需求、提前关闭需求 |
| 招聘中且 HC 已满 | 暂停招聘、取消需求、提前关闭需求 |
| 已暂停 | 取消需求、提前关闭需求 |
| 已完成、已取消、已关闭 | 恢复招聘 |

“暂停招聘”表示暂时停止且未来预计继续；“标记招聘完成”表示 HC 目标正常完成；“取消需求”表示业务方撤销；“提前关闭需求”表示招聘已启动但决定终止。四者必须使用不同文案，不能继续都叫“关闭需求”。

调整优先级、转派负责人、暂停、完成、取消、关闭和恢复必须填写原因，并调用现有需求专用接口。不得通过通用编辑接口直接改状态、优先级或负责人。

## 5. 面试管理操作规则

### 5.1 主操作

沿用当前按状态计算下一步的逻辑：

| 当前状态 | 主操作 |
| --- | --- |
| 待处理改约 | 处理改约 |
| 待安排或因改约待重新安排 | 安排面试 / 重新安排 |
| 已安排且尚未开始 | 调整安排 |
| 面试时间已到、尚未确认 | 确认已面试 |
| 待反馈 | 催反馈 |
| 已完成 | 查看反馈 |

### 5.2 更多操作菜单

根据记录是否存在对应内容显示：

- 查看面试详情；
- 查看候选人简历；
- 查看历史面试；
- 查看改约记录；
- 调整本场安排；
- 取消本场面试。

如果“调整安排”已经是当前主操作，菜单不再重复显示。已确认面试、待反馈和已完成记录不再提供调整或取消；取消仅对仍有效的已安排任务开放，并继续要求填写取消原因。

更换面试官、修改时间和地点统一进入现有调整面试弹窗，不拆成多个会产生状态冲突的入口。

## 6. 简历库操作规则

### 6.1 主操作

保留当前候选人状态推导出的唯一业务主操作，例如：

- 加入招聘流程并推送；
- 推送业务筛选；
- 补充并再次推送；
- 安排或查看面试；
- 查看 Offer；
- 进入淘汰流程处理。

解析中、待确认或当前没有可执行业务动作时不伪造主按钮，继续显示明确原因。

### 6.2 更多操作菜单

- 查看候选人详情；
- 编辑简历信息；
- 查看招聘流程；
- 收藏或取消收藏候选人；
- 转到其他需求，仅对有活动流程且当前角色有权限的候选人显示；
- 进入流程处理，仅对已经进入招聘流程的候选人显示。

当前独立的收藏、查看图标收进菜单，减少操作列堆叠。查重合并继续保留在页面顶部的专用入口；同名或相同文件提示不能直接变成自动合并、删除操作。

## 7. Offer 操作规则

### 7.1 主操作

- OA 未登记时显示“登记 OA 结果”；
- 已登记时显示“更新 OA 结果”。

### 7.2 更多操作菜单

- 查看候选人详情；
- 查看对应需求；
- 查看招聘流程；
- 查看已完成面试。

这些操作只做现有真实页面之间的准确跳转。菜单不加入自动发送、自动审批、撤回 OA 或外部系统同步，保持 Offer 一期边界不变。

## 8. 用户管理操作规则

### 8.1 主操作

- 编辑资料：维护成员姓名等基础信息。

### 8.2 更多操作菜单

- 查看成员详情；
- 调整角色与部门；
- 重置密码；
- 启用或停用账户，根据当前账号状态二选一显示。

不提供删除成员。停用账户和重置密码需要二次确认；不能停用当前登录管理员，也不能让组织失去最后一个启用的管理员，继续以后端规则为最终保护。

## 9. 技术边界

新增一个公共行操作菜单组件，只负责菜单外观、定位、键盘、关闭行为和危险色，不包含招聘业务判断。每个业务模块用独立的纯函数，根据记录状态和当前角色生成主操作及菜单项。

本次优先复用现有能力：

- 需求编辑、关闭、恢复、优先级调整和负责人转派接口；
- 候选人详情、收藏、流程处理和转需求接口；
- 面试安排、调整、取消、提醒、确认完成、详情及历史接口；
- Offer OA 结果登记和现有页面路由；
- 用户更新、启停账号和重置密码接口。

前端缺少调用封装时只补齐对应现有后端接口，不新增平行业务接口。若实现时发现某项操作没有真实接口或权限边界不完整，该操作暂停开发并回到产品确认，不能用前端假成功代替。

## 10. 错误与刷新

- 状态变更、转派、取消面试、重置密码和停用账户在确认期间锁定重复提交。
- 成功后刷新当前列表，并关闭菜单或确认弹窗。
- 409 状态冲突提示“数据已变化，请刷新后再操作”，随后读取最新状态。
- 403 权限错误提示当前角色无权执行，不保留看似可点击的按钮。
- 输入原因或表单提交失败时保留用户已填写内容，不能清空后只显示通用报错。

## 11. 验证标准

1. 五个页面统一使用公共菜单组件，没有各自复制点击外关闭和定位逻辑；
2. 每行最多一个主按钮，主按钮不在菜单中重复；
3. 菜单随状态和角色变化，高风险操作需要确认及原因；
4. 招聘需求四种结束语义保持独立；
5. Offer 不出现一期未接入能力；
6. 候选人没有删除或自动合并入口；
7. 用户管理不能删除成员或绕过最后管理员保护；
8. 菜单不会被表格、浏览器底部或右侧裁切；
9. 鼠标、键盘、Escape、点击外关闭均可用；
10. 单元测试、契约测试、类型检查、代码规范、正式构建和 Tabbit/浏览器端到端验证全部通过。
