# Test/SIT 稳定性与技术债定向治理设计

## 1. 目标

以公司 GitLab `cfpd/test` 当前提交 `b93105b` 为唯一代码基线，在不改变现有业务流程、页面效果、角色权限和数据口径的前提下，完成一轮可验证的技术债治理，让后续开发更容易定位问题、修改局部代码并稳定交付。

本轮交付标准是 **Test/SIT 内部试用稳定版**，不是生产上线认证。最终代码直接提交并推送到 `https://git.ymdd.tech/cfpd/zhipin-mvp.git` 的 `test` 分支，不触发 Libra 或 SIT 部署。

## 3. 治理原则

1. **稳定优先**：只修复能够被测试、构建、静态检查或真实运行证据证明的风险。
2. **行为不变**：不新增业务功能，不改变角色权限、流程状态、BI 口径、页面文案和视觉结构。
3. **边界优先于行数**：大文件只有在混合了多类职责并影响安全修改时才拆分，不为追求漂亮数字机械拆文件。
4. **先测试后重构**：每个被触达模块先补行为或边界测试，再做等价重构。
5. **小步提交**：测试护栏、前端治理、后端治理、发布门禁和文档分别形成可回退提交。
6. **保护用户文件**：不覆盖、清理、格式化或提交任务开始前已有的未跟踪文件。
7. **不扩大架构**：保持 React + Flask 的模块化单体，不引入微服务、第二套框架或第二套权限体系。

## 4. 治理范围

### 4.1 基线与门禁可信度

- 在干净的 Git 提交树中复现统一发布门禁，区分“代码候选失败”和“原工作区存在用户文件”。
- 核对 `check-sit-release.sh`、GitLab CI 和本地脚本实际覆盖范围，修复命令、环境变量或结果判断不一致的问题。
- 浏览器冒烟不以安装了 Google Chrome 为前提；继续使用 Playwright 自带 Chromium，用户日常默认浏览器仍是 Tabbit。
- 对第三方库产生且不影响项目行为的已知警告，只能在确认来源和适用范围后做精确处理；不得全局吞掉告警。
- 保留依赖安全、迁移唯一性、构建体积和敏感文件检查的现有硬门槛，不降低标准换取绿灯。

### 4.2 前端可维护性

- 优先审查当前最大的正式业务模块：候选人工作台控制器、招聘需求候选人抽屉、招聘需求页面、主布局和管理分析异步包。
- 只拆分同时承担数据请求、状态编排、业务动作和视图渲染的模块；提取后的单元必须有单一职责、明确输入输出和独立测试入口。
- 保持 `pages -> features -> shared components/api` 的单向依赖，不允许 feature 反向引用 page。
- 保持路由按需加载、正式路由不依赖 Mock、统一错误翻译、统一弹层生命周期和现有无障碍行为。
- 对接近体积红线的入口包分析真实依赖来源；仅在能保持行为并增加安全余量时调整加载边界，不为了数字改动业务代码。

### 4.3 后端可维护性与稳定性

- 优先审查体积较大的 API 与服务模块：agent、candidates、interview、demand、pipeline 和 app factory。
- API 层只保留参数接收、权限入口、服务调用和响应转换；可复用业务规则、校验和状态变更必须归属服务层。
- 对宽泛异常捕获逐处判断：后台 worker、注册中心关停等需要容错的地方保留并补充明确日志或测试；请求链路中可能掩盖真实错误的地方收紧处理。
- 不在本轮机械拆分 `models.py`。SQLAlchemy 模型集中定义本身不是故障证据，贸然拆分会增加循环导入和迁移风险。
- 不更改数据库表结构；若审查发现必须依靠 schema 才能修复的数据完整性问题，停止该项并单独记录，不在本轮暗中加迁移。

### 4.4 测试盲区与回归保护

- 保留现有 691 项后端测试和 168 项前端契约测试，新增测试只覆盖本轮实际触达的边界和回归风险。
- 运行五角色浏览器最小冒烟，至少验证登录、角色菜单、核心列表、详情打开/关闭和整页错误兜底。
- 对拆分模块增加等价行为测试，确保数据请求、筛选、选择、提交、错误恢复和权限判断没有变化。
- 验证本地隔离环境和发布脚本的启动、健康检查、停止与失败退出码；测试数据继续使用可丢弃本地数据。
- 不用大量源码字符串断言替代真实行为测试；现有契约测试继续保留，新测试优先验证公开接口和用户行为。

### 4.5 文档真源

- 更新 `README.md` 和 `docs/README.md` 中过期的分支、提交、日期和候选状态描述。
- 若运行命令、CI 变量或验收方式发生变化，同步更新 `RUNNING.md`、`DEPLOYMENT.md` 或对应检查说明。
- 本轮不改变产品流程、接口字段、端口、BI 口径或 AI 助手行为，因此 PRD、BI 设计和业务交接文档原则上不改；如实施中实际触及这些内容，必须重新评估并同步文档。

## 5. 实施顺序

1. 冻结并记录 `b93105b` 基线，在独立干净工作树复现全量门禁。
2. 审计发布脚本、CI、浏览器冒烟和构建体积，先修门禁不一致及测试盲区。
3. 以新增测试保护前端高风险模块，再做最小等价拆分。
4. 以新增测试保护后端高风险调用链，再把错位职责收敛到服务层。
5. 运行分层测试和真实浏览器冒烟，修复回归。
6. 同步当前真源文档，在干净提交树运行最终全量门禁。
7. 检查任务 diff、提交记录和远程 `cfpd/test`，推送后用远程 SHA 复核。

任一步骤如果发现需要改变产品行为、数据库结构或权限口径，暂停该子项并记录为后续任务，不擅自扩大范围。
