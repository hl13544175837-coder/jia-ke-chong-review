# PGS 真人角色与智聘工作台接线设计

## 目标

第一轮用公司真人账号“李四（工号 `100002`）”跑通面试官角色：PGS 授权决定他进入面试官工作台，后端把他识别为真实的 `interviewer` 用户，只返回分配给李四本人的需求、候选人、业务筛选和面试任务。

本设计严格区分两个概念：

- **角色决定页面**：招聘专员进入 `/dashboard`，面试官进入 `/interviewer/dashboard`。
- **账号决定数据**：不同面试官共用同一套面试官页面，但后端按当前登录人的用户 ID、工号、组织和任务分配过滤数据。

因此不为“面试官一、面试官二”复制两套页面，也不使用前端隐藏按钮代替后端权限。

## 当前问题

本地 `interviewer01@mvp.local` 是可工作的演示账号，能证明面试官页面和后端 RBAC（基于角色的权限控制）存在，但不能证明 PGS 真人授权已经接通。

测试环境目前有两套没有闭环的权限信号：

1. PGS 返回当前用户的菜单树。
2. 智聘前后端分别使用构建参数和运行参数中的“工号 → 技术角色”映射。

前端虽然请求了 PGS 菜单树，但当前侧边栏和首页跳转主要按智聘技术角色判断，没有用角色工作台菜单编码完成角色识别。结果是：PGS 中把李四授予“面试官”后，智聘仍可能按默认 `recruiter` 展示招聘专员工作台。

## 方案比较

### 方案 A：PGS 工作台菜单 + 后端工号角色双重对齐（本轮采用）

PGS 菜单决定用户应进入哪类工作台；后端工号映射决定用户能读写哪些业务数据。登录时检查两者一致，不一致就给出明确错误，不允许出现“页面像面试官、接口却是招聘专员”的半连接状态。

优点是能直接复用现有 PGS 和后端 RBAC，改动范围可控；缺点是发布时必须保证 PGS 与前后端环境配置同步。

### 方案 B：只使用工号映射

不用 PGS 菜单决定角色，继续由前后端配置文件识别工号。实现最快，但用户在 PGS 中配置角色后不会自然生效，与当前目标不符，不采用。

### 方案 C：后端实时调用 PGS 权限接口

由后端直接向 PGS 查询并缓存用户权限，形成单一权限真源。长期更理想，但需要公司内部接口、服务身份、超时降级和缓存策略证据，本轮没有这些现场信息，暂不扩张范围。

## 菜单和角色契约

五类公司角色使用各自唯一的工作台标记：

| PGS 菜单名称 | 菜单编码 | 智聘技术角色 | 首页路由 |
|---|---|---|---|
| 系统管理员工作台 | `dashboard_admin` | `admin` | `/dashboard` |
| 招聘主管工作台 | `dashboard_manager` | `manager` | `/dashboard` |
| 招聘专员工作台 | `dashboard_recruiter` | `recruiter` | `/dashboard` |
| 面试官工作台 | `dashboard_interviewer` | `interviewer` | `/interviewer/dashboard` |
| 人力资源总监工作台 | `dashboard_hr_director` | `hr_director` | `/director/cockpit` |

同一个账号只能命中一个角色工作台标记。若同时返回两个标记，登录失败并提示联系管理员清理重复授权；若没有返回任何标记，采用 `/api/auth/me` 返回的后端真实角色进入对应工作台，避免构建期默认 `recruiter` 与管理员等真实账号冲突。PGS 一旦返回工作台标记，仍必须与后端角色一致。

普通功能菜单（如 `demands`、`candidates`、`interviews`、`bi`）只负责入口显示，不能单独推断业务角色。面试官角色第一轮只保留实际验收需要的菜单，不因页面暂时隐藏而放宽后端接口。

## 登录与权限数据流

1. 用户通过公司网关登录，取得真实工号和登录 token。
2. 前端读取 PGS 当前用户菜单树，从唯一的工作台菜单编码识别页面角色。
3. 前端携带登录 token 和真实工号调用 `/api/auth/me`，取得后端认定的技术角色；菜单角色与后端角色不一致时停止进入业务页面。
4. 两边一致后，前端按角色跳转到对应工作台，并按菜单编码过滤可见入口。
5. 每个业务请求继续携带真实工号 `X-Emp-Code`。
6. 后端按 `AUTH_GATEWAY_ROLE_MAP` 将工号映射到技术角色，并创建或复用 `<工号>@gateway.local` 的内部用户记录，用于外键、审计和数据归属。
7. 后端接口继续以当前用户 ID、角色和组织为最终权限边界；客户端传来的页面状态不能扩大权限。

李四首轮发布配置必须包含：

```text
前端菜单：dashboard_interviewer
前端构建映射：100002:interviewer
后端运行映射：100002:interviewer
```

## 数据隔离要求

两名面试官登录同一页面时：

- 只能看到分配给自己的面试、业务筛选和允许查看的候选人信息。
- 不能通过修改 URL、候选人 ID、需求 ID 或接口参数读取另一名面试官的任务。
- 提交反馈时，后端必须确认该面试任务确实分配给当前用户。
- PGS 菜单授权不能替代上述后端判断。

已有面试接口和服务层过滤继续作为唯一业务权限 owner；本轮补充两个不同面试官的数据隔离回归测试，发现缺口时在原服务层修复，不在页面散落临时判断。

## 错误处理

- 同时存在多个角色工作台标记：拒绝进入业务页面，显示“账号配置了多个工作台角色”。
- PGS 菜单接口失败：显示公司权限加载失败及重试入口，不把失败当成全部菜单可见。
- PGS 工作台角色与后端角色不一致：阻断业务操作并说明两边配置值，避免静默串权限。
- 未映射工号：后端继续按最小权限 `recruiter` 处理，但测试验收必须标记为配置未完成。

## 验收

第一轮必须形成以下证据链：

1. PGS 中李四 `100002` 绑定 `interviewer`，并获得 `dashboard_interviewer`。
2. 李四登录后落在 `/interviewer/dashboard`，看不到招聘专员工作台入口。
3. 后端识别的当前用户角色也是 `interviewer`。
4. 李四只看到分配给自己的数据；用第二名面试官反向验证双方数据不串。
5. 李四直接访问招聘专员路由或调用无权接口时被拒绝，并留下审计证据。

第一轮跑通后，再沿用同一契约接招聘专员；经理、管理员和人力资源总监另行确认 PGS 菜单编码后扩展，不在本轮猜测。
