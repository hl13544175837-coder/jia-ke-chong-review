# 面试改约、取消后重排与全程留痕设计

## 目标

在现有“我的面试”和“面试管理”内补齐可闭环的改约流程，不新增页面、不依赖外部日历接口。面试官可以申请改约，招聘专员确认后才生效；招聘专员也可以主动调整。无论只改时间、换面试官，还是取消后重新安排，都要通知对应人员并保留完整历史。

## 第一性原理

1. 面试安排是多人约定，任何一方提出变化都不能悄悄覆盖当前约定。
2. “申请改约”和“改约已生效”是两个状态；面试官提交申请后，原安排继续有效，直到招聘专员确认。
3. 已取消记录属于事实，不能恢复成“从未取消”；重新激活必须创建一条新任务，并关联旧任务。
4. 下一位面试官需要知道发生过什么，但只能看到排期相关信息，不能看到越权数据。
5. 同一面试官只改时间时，没有必要制造第二条面试任务；直接更新原任务，同时写入不可变的改约记录。
6. 候选人的招聘阶段不能因为一次改约被错误移出“面试中”。

## 角色与入口

| 角色 | 现有位置 | 新增能力 |
|---|---|---|
| 面试官 | 我的面试 > 面试详情 | 申请改约，填写原因和 1～2 个建议时间；查看自己的申请状态和排期历史 |
| 招聘专员 | 面试管理 > 候选人详情/调整安排 | 处理待改约、直接调整、拒绝、取消后待重排、重新安排；查看完整排期历史 |
| 经理/管理员 | 面试管理 | 按现有需求权限处理和查看，不扩大组织范围 |

## 数据模型

新增 `interview_reschedule_requests`，一条记录既表示一次申请，也表示一次已经发生的主动调整。它保存旧安排快照和最终安排快照，因此原任务以后被取消或替换也不会丢历史。

核心字段：

- 归属：组织、需求、候选人、原面试任务、替代面试任务。
- 来源：`interviewer_request` 或 `recruiter_direct`。
- 状态：`pending`、`approved`、`rejected`、`waiting_reassignment`、`resolved`。
- 申请信息：申请人、申请时间、原因、最多两个建议时间。
- 原安排快照：原面试官、原时间、原地点。
- 最终安排快照：最终面试官、最终时间、最终地点。
- 处理信息：处理人、处理时间、处理说明。

约束：同一面试任务同时只能有一个 `pending` 申请；组织、需求和角色权限必须由后端校验。

## 状态流转

### 面试官申请改约

1. 只有属于自己的、仍为 `scheduled`、未提交反馈的任务可以申请。
2. 原因必填，建议时间至少一个、最多两个，且必须是未来时间。
3. 写入 `pending` 申请并通知该需求的招聘负责人。
4. 原面试时间、地点、面试官保持不变。

招聘专员处理：

- 同意并保留原面试官：更新原任务时间/地点，申请变为 `approved`，通知申请人。
- 同意并更换面试官：原任务仍可调整时直接更新原任务，通知旧面试官和新面试官。
- 拒绝：申请变为 `rejected`，原安排继续有效，通知申请人并展示原因。
- 取消后再排：取消旧任务、释放轮次占位，申请变为 `waiting_reassignment`，候选人仍留在面试阶段。

### 招聘专员主动调整

招聘专员使用现有“调整面试安排”。保存时先记录原安排快照，再更新任务，并新增一条来源为 `recruiter_direct`、状态为 `approved` 的历史。保留同一面试官时只通知该面试官；换人时同时通知旧、新面试官。

### 取消后重新激活

1. `waiting_reassignment` 不是恢复旧任务，而是“旧任务已取消，候选人仍待安排”。
2. 招聘专员在现有面试管理中点击“重新安排”。
3. 后端创建新的面试任务，关联原申请和旧任务，并把申请更新为 `resolved`。
4. 新任务可以使用原面试官，也可以更换面试官；通知最终面试官。
5. 旧任务继续显示为已取消，历史里明确指向新任务。

## 通知规则

| 事件 | 接收人 | 文案重点 |
|---|---|---|
| 面试官提交改约 | 需求招聘负责人 | 谁申请、原时间、建议时间、原因 |
| 招聘专员同意 | 申请人、旧/新面试官去重 | 最终时间、地点、是否更换面试官 |
| 招聘专员拒绝 | 申请人 | 原安排仍有效、拒绝原因 |
| 取消后待重排 | 原面试官、申请人去重 | 原任务已取消、招聘专员将重新安排 |
| 创建替代任务 | 新面试官、申请人去重 | 新时间、新地点、替代了哪次取消安排 |
| 招聘专员主动调整 | 旧/新面试官去重 | 旧安排与新安排的关键变化 |

通知只使用现有本地站内通知，不接飞书日历、邮件或外部接口。

## 界面设计

### 面试官

- 面试详情底部增加次级按钮“申请改约”，仅可改约时显示。
- 弹窗沿用当前白底、绿色主按钮、标准字号和圆角；原因必填，建议时间最多两个。
- 有待处理申请时显示“改约待招聘专员确认”，并明确“当前安排仍有效”。
- “面试信息”内增加“排期变更记录”，按时间倒序展示旧时间、新时间、申请人、处理人、原因和结果。

### 招聘专员

- 现有面试管理行和详情显示“待改约”标记，不新增独立页面。
- 详情内显示申请内容，提供“按此时间调整”“调整后同意”“拒绝”“取消后待重排”。
- 原任务取消后，该候选人仍以“因改约待重新安排”显示，现有“安排面试”弹窗用于创建替代任务。
- 现有直接调整弹窗增加“调整原因”必填；保存后自动留痕。

## 权限与失败保护

- 面试官只能为自己的任务申请，不能自己批准、换人或取消。
- 招聘专员只能处理自己负责需求；经理和管理员沿用现有权限。
- 已完成、已有反馈、已取消的任务不能新申请改约。
- 待处理申请不能重复提交；并发处理时第二次返回“已被处理，请刷新”。
- 新时间必须在未来，且继续使用现有面试官时间冲突校验。
- 接口失败时不先改前端列表，成功后统一刷新，避免显示假成功。

## 验收标准

1. 面试官提交改约后原安排不变，招聘负责人收到站内通知。
2. 招聘专员可保留原面试官只改时间，也可更换面试官；对应人员收到通知。
3. 招聘专员拒绝后原安排仍有效，面试官看到原因。
4. 取消后候选人仍在面试阶段，显示“因改约待重新安排”。
5. 重新安排可选择原面试官或新面试官，并创建关联的新任务。
6. 面试官和招聘专员都能看到完整排期历史，旧记录不被覆盖。
7. 组织、需求、角色、冲突时间和已完成状态均有后端保护。
8. 数据库迁移、定向测试、全量后端测试、前端测试、类型检查、代码规范和构建全部通过。

## 不在本次范围

- 不新增页面，不重做面试管理架构。
- 不接第三方日历、短信、邮件或飞书消息接口。
- 不允许面试官绕过招聘专员直接让新时间生效。
- 不删除或改写历史取消记录。
