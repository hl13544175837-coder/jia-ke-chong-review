# 招聘专员 Offer 待办工作台设计

## 目标

把当前以“全部 Offer 档案”为中心的页面，改成招聘专员每天打开后能立即处理工作的待办工作台。默认回答三个问题：今天要处理什么、为什么要现在处理、下一步点哪里。

本次不更换技术栈，不重做 Offer 数据模型，不接企业微信或邮件接口。继续使用现有 React 页面、Flask API、Offer 状态和操作历史。

## 已确认的业务规则

- 默认入口为“今日待办”，不是“全部”。
- 招聘专员自己确认 Offer，不等待招聘经理审批。
- 原“审批中”对用户统一改称“待确认”。
- 流程为：草稿 → 待确认 → 待发放 → 待回复 → 待入职 → 已入职或结束。
- 招聘专员点击“确认发放”时，必须登记实际发送渠道；发送时间由系统自动记录。
- 企业微信和邮件未接通前，系统只记录线下真实操作，不冒充已经自动发送。
- 已入职、已拒绝、已撤回、已过期归入历史，不占据日常工作主列表。

## 方案选择

采用“待办优先、历史折叠”的单列表方案。

不采用纯看板：候选人较多时横向列过长，不利于搜索和批量处理。也不采用当前全量列表：首页被历史数据占满，无法体现今天的工作重点。

## 页面结构

### 1. 页面头部

- 标题：Offer 工作台。
- 说明：确认方案、记录发放、跟进回复和确认入职。
- 主按钮：新建 Offer。
- 保留从工作台或招聘需求进入时的返回入口和岗位范围提示。

### 2. 今日提醒条

只在有异常或临近事项时显示，内容包括：

- 超过 1 个工作日仍未确认的 Offer。
- 已确认但尚未登记发放的 Offer。
- 已发放超过 3 天仍未回复的 Offer。
- Offer 有效期在 2 天内到期。
- 预计入职日在 3 天内但尚未确认到岗。

提醒条中的每项可以直接切换到对应筛选结果，不做无效展示。

### 3. 状态导航

顺序固定为：

1. 今日待办：草稿、待确认、待发放、需要跟进、临近入职的 Offer。
2. 草稿。
3. 待确认。
4. 待发放。
5. 待回复。
6. 待入职。
7. 历史记录。

状态数量为 0 时仍可作为筛选标签查看空状态，但不显示成需要处理的提醒。

### 4. 搜索与筛选

常驻一行：

- 搜索候选人、岗位、需求编号。
- 岗位或招聘需求筛选。
- 负责人筛选。
- 风险筛选：已超时、即将到期、临近入职。
- 排序：紧急优先、最近更新、预计入职日。

低频条件收进“更多筛选”，不再把筛选藏在每个表头里。已生效条件显示为可单独删除的标签，并支持一键清空。

### 5. 待办列表

列表列顺序：

- 候选人 / 岗位。
- 当前节点与等待时长。
- 薪酬方案。
- Offer 有效期或预计入职日。
- 风险提示。
- 下一步。

招聘需求显示“岗位名称 + 需求编号”，不再只显示难辨认的编号。

每行只保留一个主操作：

- 草稿：继续编辑。
- 待确认：确认 Offer。
- 待发放：登记发放。
- 待回复：登记候选人回复；次操作为记录跟进。
- 待入职：确认入职；次操作为记录跟进。
- 历史记录：查看记录。

点击行打开同页详情抽屉，不跳走。主操作按钮直接打开抽屉中对应表单，减少二次寻找。

## 详情抽屉

抽屉顶部先展示“当前状态、下一步、已等待多久”，再展示薪酬、岗位、预计入职日等信息。

交互文案调整：

- 提交审批 → 提交确认。
- 待审批 → 待确认。
- 审批通过 → 确认无误。
- 审批人 → 确认人。
- 记录为已发放 → 登记发放。
- 查看 / 处理 → 使用当前节点对应的明确动作。

招聘专员可对自己有权限管理的 Offer 执行“确认无误”。后端仍沿用 `pending → approved` 状态转换，避免数据库迁移和历史数据失效，只调整权限和用户文案。

登记发放表单必须包含：

- 发送渠道：企业微信、邮件、线下、其他。
- Offer 有效截止日期，默认 14 天后。
- 备注，可选。

系统记录操作者、操作时间、渠道和备注。页面必须说明“仅登记发送结果，当前未自动调用企业微信或邮件”。

## 数据与排序口径

- 今日待办只包含未结束状态：`draft`、`pending`、`approved`、`sent`、`accepted`。
- 历史记录包含：`declined`、`withdrawn`、`expired`、`onboarded`。
- 紧急优先级从高到低：已过期风险、回复超时、待确认超时、临近入职、普通待办。
- 等待时长从该节点对应时间计算；缺失节点时间时回退到最近更新时间。
- 岗位范围入口继续严格排除历史 Offer，除非用户主动进入历史记录。

## 权限与错误处理

- 招聘专员、招聘经理和管理员均可确认 Offer；面试官不可访问。
- 操作前继续校验组织、招聘需求归属和需求是否可写。
- 并发状态变化返回 409 时，提示“Offer 状态已变化”，刷新详情，不重复提交。
- 登记发放缺少渠道时前端禁止提交，后端同时校验。
- 接口失败保留用户输入，显示可理解的错误，不把失败操作显示成成功。

## 测试与验收

- 先补失败测试，再实现。
- 招聘专员可完成：新建草稿 → 提交确认 → 自己确认 → 登记发放 → 登记接受 → 确认入职。
- 默认进入“今日待办”，5 条已入职历史记录不再占据首页。
- 每个状态至少有一条演示数据或自动化构造数据覆盖对应按钮。
- 登记发放必须真实保存渠道、时间和操作历史。
- 今日提醒、风险排序、搜索、岗位筛选和返回来源均需自动化测试与浏览器实机验收。
- 运行前端全量测试、后端全量测试、类型检查、代码规范检查和正式构建。

## 不在本次范围

- 企业微信或邮件真实发送。
- 电子签名、合同模板引擎和薪酬 OA 接口。
- 批量发放 Offer。
- 修改既有 Offer 状态枚举或迁移历史数据库。
