# 03 BI 看板设计 — 智聘招聘系统（BI 口径真源）

> v1.3 ｜ 2026-07-11 ｜ demand-scoped P0
>
> 定位：BI 只用于看进度、找卡点和明确当前协同责任，不用于个人绩效排名、奖金或历史功劳结算。

## 0. 状态与使用边界

`demand_id` BI 已在当前代码候选中完成服务层、API、前端类型和页面收口。SIT 测试数据可清空或重建；实际部署与页面生效状态仍以 CFPD、Libra、schema revision、测试站资产和受控 API 现场证据为准，真实数据指标需另行对账。

当前代码由 `bi_service` 以 `RecruitmentDemand` 为入口，流程、面试反馈、Offer、HC、告警和当前责任均按 `org_id + demand_id` 计算；`job_id` 只保留岗位画像投影。`/bi/job/:job_id` 仅在 Job 能唯一解析一个 Demand 时兼容代理，多 Demand 歧义返回 409，不聚合兄弟 Demand。团队和专员契约不再返回个人绩效、排名或转化率字段。

口径裁决顺序：

1. 产品范围看 [01 PRD](./01_PRD.md)。
2. 当前代码与接口真相看 [SDD](./SDD-智聘招聘系统-v1.0.md)。
3. 数据迁移和回滚看 [10 demand_id 迁移与回滚手册](./10_demand_id迁移与回滚手册.md)。
4. 任何页面文案、AI 回答或临时 SQL 都不得改写本文的业务口径。

## 1. BI 必须回答什么

| 使用者 | 核心问题 |
|---|---|
| 招聘专员 | 我当前负责哪些 Demand，哪个候选人要先处理，哪个轮次缺反馈？ |
| 招聘经理/负责人 | 哪个 Demand 超期、停滞或 HC 有缺口，现在应该协调谁？ |
| 面试官 | 我被分配了哪些轮次，哪些已到时但尚未反馈？ |
| 人力资源总监 | 哪些岗位需要管理升级，当前责任人是谁，应该调整资源还是优先级？ |
| 管理员 | 数据是否跨组织、串 Demand、缺关键字段或失去可追溯性？ |

BI 不回答：“谁比谁优秀”“谁应得多少奖金”“转派前的所有成果算给谁”。这些需要独立的事件时点责任模型、业务批准与合规设计，不属于 P0。

## 2. 口径主键与事实 Owner

### 2.1 核心主键

| 业务事实 | 目标归属键 | 说明 |
|---|---|---|
| 职位/JD 标准与候选人匹配 | `job_id` | 同一职位模板可被多个 Demand 复用 |
| 候选人流程、面试、Offer、HC、审计、BI | `demand_id` | 兄弟 Demand 必须独立计算 |
| 候选人主档 | `candidate_id` | 一个自然人不因转需求复制主档 |
| 候选人在需求下的应聘关系 | `(org_id, candidate_id, demand_id)` | `CandidateDemandFlow` 唯一 |

### 2.2 责任归属

- 当前 Demand 负责人回答“现在谁应该接住”。
- `pipeline_stages.updated_by`、`interview_feedback.interviewer_id`、`events.actor_id` 回答“这一步是谁做的”。
- “面试待补反馈”提醒中，`interviewer_id/interviewer_name` 是应实际提交反馈的面试官，`owner_hr_id/owner_name` 是负责协调跟进的当前 Demand 负责人；两者不得互相替代。
- Demand 转派可更新活动 Flow 与当前候选人责任，但历史推进人、面试官和 actor 不重写。
- 当前责任数字不等于事件发生时的历史功劳。

## 3. Demand 运营指标

### 3.1 当前阶段与漏斗

每个未软删除候选人的 `(candidate_id, demand_id)` 只取 `pipeline_stages` 最新一行。不能直接对 append-only 历史按 `stage` 分组；团队“当前流程人数”只聚合开放 Demand，已暂停/关闭/完成等历史 Demand 仍可在需求明细中查看，但不混入当前团队漏斗。

| 指标 | 口径 |
|---|---|
| 当前流程人数 | `pending / ai_screen / business_review / interview / offer` 的当前人数 |
| 已入职 | 当前阶段 `onboarded`；该阶段只能由已接受 Offer 的确认入职事务生成 |
| 已淘汰 | 当前阶段 `rejected` |
| 已转出 | 当前阶段 `transferred`，单独展示，不计入淘汰 |
| HC 完成度 | `onboarded_count / headcount` |
| 建议完成 | `onboarded_count >= headcount`，只返回 `completion_suggested=true`，不自动关闭 Demand |

### 3.2 停滞与待办

| 指标 | 口径 | 下钻 |
|---|---|---|
| 阶段停留 | 当前最新阶段时间到当前时间 | Demand + stage + candidate |
| 业务待反馈 | 当前 `business_review` | Demand + candidate + 当前负责人 |
| 面试待补反馈 | 面试时间已过，该 assignment 无有效反馈，且状态不是 `cancelled/canceled` | Demand + round + assignment + interviewer（应补反馈）+ owner（协调跟进） |
| 需求逾期 | Demand 未终止且 `target_date < today` | Demand 详情 |
| HR 尚未推荐 | Demand 达到业务约定时长且从未有候选人进入流程 | Demand 详情/匹配入口 |
| 当前无在流程候选人 | Demand 有历史候选人，但当前只剩 `rejected/transferred/onboarded` 等终态；HC 已满足时不重复告警 | Demand 详情/匹配入口 |

目标日期预警、停滞、无推荐、低面试转化候选人量和需求开放过久的阈值由组织级 `kpi_standards` 统一提供，同一份配置同时驱动 Demand 卡点标记与 BI 告警，不得在页面端另设阈值。当组织尚未保存配置或存量版本缺字段时，后端分别使用目标日期提前 14 天、阶段停滞 7 天、无推荐 7 天、推荐 20 人仍无面试和开放过久 60 天的默认值。`block_categories` 同样按组织配置将 BI 告警归类；这些配置只表示组织流程预警标准，不用于个人绩效。

`high_if_status_paused_or_closed`、`high_if_zero_fill_and_blocked`、`attention_hc_gap_ratio`、`attention_if_blocked` 和 `process_health_thresholds.green/yellow` 因当前没有经业务批准的 Demand 风险等级或健康分公式，不属于正式可编辑口径。后端会忽略旧存量 JSON 中的这些字段，不将它们计算成风险分、个人分或绩效结论。

### 3.3 面试协同

一面、二面、终面和加面是 `interview` 下的任务轮次，不是用于跨 Demand 对比的新主阶段。

| 指标 | 口径 |
|---|---|
| 已安排 | `InterviewAssignment` 记录数，按 Demand 和轮次展示 |
| 已反馈 | 与 assignment 关联的有效反馈数 |
| 本轮已完成 | 有效主面试官已提交反馈 |
| 辅助反馈 | 非主面试官反馈，不单独使本轮完成 |

面试反馈只记录业务事实和建议；主面试官推荐“进入下一轮”时自动创建下一轮待安排任务，反馈不自动淘汰、不自动进入 Offer、不改变需求阶段归属（BI 归属口径不变）。

面试协同的事实唯一性由 revision `20260711_02` 兜底：有效主面试安排用 `primary_slot=round_sequence`，唯一索引约束 `(org_id,demand_id,candidate_id,primary_slot)`；同一 assignment 的 feedback 也有唯一索引。迁移发现存量重复会中止并输出冲突，不自动选择赢家。

### 3.4 来源渠道

来源渠道仍按候选人入库 cohort 观察，但后续流程结果必须通过 `demand_id` 关联，不得把同 Job 下的兄弟 Demand 合并为一条流程。

标准渠道：`BOSS直聘`、`58同城`、`猎聘`、`鱼泡直聘`、`智联招聘`、`前程无忧`、`内推`、`官网`、`LinkedIn`、`其他`。别名在后端统一归一；P0 不实现渠道 ROI 或外部渠道自动对接。

当前运营 BI 响应不含渠道质量、ROI 或个人转化指标；来源字段继续保留，为后续单独定义 cohort 与成本口径做准备。

## 4. 事件与可追溯性

所有关键动作写可查询 `demand_id`；对当前阶段、面试轮次、Offer 和 HC 以业务事实表为准，`events` 用于追责和操作留痕。

| action | 必备归属 |
|---|---|
| `demand.created` / `demand.closed` / `demand.restored` / `demand.owner_reassigned` | demand_id, actor_id；暂停/取消/完成/关闭由 `demand.closed` payload.status 区分，原因/变更写 payload |
| `pipeline.moved` | demand_id, candidate_id, from, to, actor_id |
| `pipeline.transferred` | from_demand_id, to_demand_id, candidate_id, reason, actor_id |
| `interview.assigned` / `interview.feedback` / `interview.assignment_cancelled` | demand_id, candidate_id, assignment_id, round, actor/interviewer；取消含 reason |
| `offer.saved` / `candidate.onboarded` | demand_id, candidate_id, actor_id |

迁移前的 actor、面试官和历史事件不随 Demand 负责人转派重写。

## 5. 看板层级与下钻

页面必须区分三种状态：请求进行中显示加载态；请求失败显示“数据暂不可用”、错误原因和重试入口；只有请求成功且确无业务事实时才显示空态与下一步入口。网络/权限/服务错误不得转换成 `0`、空数组或“暂无数据”。

### 5.1 团队协同总览

- Demand 总数与状态分布；团队当前漏斗只统计开放 Demand。
- 逾期、长时间无推荐、业务待反馈、面试待补反馈、HC 建议完成。
- 每个数字都携带当前筛选条件进入 Demand 或候选人明细。
- 招聘经理先按当前负责人查看在招 Demand、剩余 HC、在途候选人、卡点和待补反馈，再下钻该负责人名下 Demand；该视图是当前责任协同，不是个人排名。
- 人力资源总监的驾驶舱负责当天风险和升级决策，组织数据看板负责趋势和报表复盘；风险提醒必须直达具体 Demand、负责人和建议跟进动作。
- 总监“审批与风险”是只读监督入口：招聘经理负责需求与 Offer 的实际审批，总监负责识别超时、升级资源和调整优先级。

### 5.2 Demand 详情

- 需求事实：部门、城市、HC、负责人、目标日期、状态。
- 流程：阶段分布、停滞时长、已转出/已淘汰区分；当前阶段卡下钻当前阶段，“全部候选人”使用 `stage=all` 下钻全阶段。
- 协同：待补反馈要分别展示“应补反馈面试官”和“Demand 协同负责人”，同时保留主面试官与当前候选人责任信息。
- 动作：进候选人明细、面试任务、Offer 或需求操作；Offer 总数展示具体 Offer 记录并进入候选人事实，不冒充当前 `offer` 阶段人数。

### 5.3 候选人事实

从任何 BI 数字下钻后，都必须能看到具体 `demand_id`、当前阶段、最后更新时间、当前负责人、待办与历史操作人。页面不得只展示无法反查的聚合数字。

### 5.4 已入职视图的周期边界

`/dashboard/hired` 当前读取真实 `OfferRecord`：累计和本月入职人数来自 `status=onboarded` 记录；确认入职会在同一事务把该 Offer 与对应 Pipeline 最新阶段一并写为 `onboarded`，因此已入职页、流程漏斗和 HC 不允许由普通 Pipeline 推进产生分裂事实。页面用 `OfferRecord.created_at` 到 `onboarded_at` 的日期差时，只能命名为“Offer 至入职周期”。它不是完整招聘周期，因为当前接口没有明确返回招聘起点或后端计算后的完整周期字段。

如果后续要展示“平均招聘周期”，必须先由后端和本文定义统一起点、终点、排除规则与聚合字段，前端只展示该明确结果，不能把其他日期差改名冒充。

## 6. 当前代码候选 API 契约

> 下列契约已由本地测试约束，但只有取得 CFPD、Libra、schema 与受控 API 证据后才能宣称在 SIT 生效。

| API | 作用 |
|---|---|
| `GET /api/bi/overview` | manager/admin 的组织内运营总览：`purpose`、Demand 最新阶段漏斗、可下钻 `alerts` 和 `demands`；不含人员绩效 |
| `GET /api/analytics/overview` | manager/admin/hr_director 的组织真实统计：招聘趋势、部门、来源、Demand、周期和待关注事项；总监现有四个只读页面统一使用该接口 |
| `GET /api/bi/demand/:demand_id` | 单 Demand 漏斗、阶段停留、待反馈、Offer、HC 和候选人下钻 |
| `GET /api/bi/staff/:id` | 本人或 manager/admin 查看该专员当前负责的开放 Demand 与 `workload`；只含活动 Demand/候选人、业务待反馈、面试、Offer、待补反馈，不含排名或绩效率 |
| legacy `GET /api/bi/job/:job_id` | 仅当 Job 唯一解析一个 Demand 时返回 `compatibility.mode=single_demand`；多 Demand 歧义返回 409 `demand_id_required`，不做隐式 aggregate |

权限在后端以 `org_id + demand_id + role/current owner` 校验。Job 模板维护人不自动获得同 Job 下所有 Demand 的 BI 访问权。AI 的 Demand 指标工具复用同一 `bi_service`；招聘专员概览中的面试数量则按其可见 Demand/候选人单独收敛，不能绕过 BI 权限。

## 7. 迁移与对账门禁

把本代码候选部署并切换到目标环境前必须满足：

1. 核心流程事实 `demand_id` 无空值。
2. 每行 `job_id == demand.job_id`，跨组织和孤儿关系为 0。
3. 歧义 bundle 均有业务批准映射，脚本没有默认选“最新 Demand”。
4. 事实表旧记录数守恒：每条旧记录恰好映射一次。
5. 单 Demand Job 的新旧口径 shadow comparison 一致；多 Demand Job 按业务事实逐条对账，不强求旧的错误去重数与新数相等。
6. MySQL/PostgreSQL/SQLite 按实际目标引擎验证；试点若使用 MySQL，必须先有临时库恢复证据。

## 8. 实施克制

- 先做 Demand 进度、卡点、待补反馈、HC 和可下钻明细。
- 不做个人强制排名、正式考核、招聘成本或复杂预测。
- 不为了看板提前引入第二套 BI 数据库、微服务或新前端框架。
- 不在没有代表性数据时展示容易被误解为真实结论的图表；空态应引导建需求、加入候选人或补齐反馈。
