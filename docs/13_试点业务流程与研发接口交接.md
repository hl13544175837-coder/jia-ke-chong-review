# 试点业务流程与研发接口交接

> 确认日期：2026-07-27
>
> 适用前端：`readdy-frontend`，本地端口 `5190`
>
> 状态：本仓库内部流程、接口路径、权限和本地持久化已实现；公司 OA、企业微信、邮件、短信和候选人触达由公司研发接入。

## 1. 试点范围

本轮只固化几名公司同事使用的最短招聘闭环：

`需求生效 → 当前需求内选人/导入简历 → HR 初筛并推送 → 业务筛选 → HR 安排面试 → 面试官评价 → HR 决策 → Offer 阶段与 OA 结果登记 → 确认入职`

一期暂时隐藏 AI 助手、BOSS 自动化和 KPI 标准。对应源码可以保留，但不能出现在试点导航，也不能用演示结果冒充真实业务数据。

## 2. 角色职责

| 产品角色 | 主要职责 |
|---|---|
| 业务负责人 / 面试官 | 按模板填写招聘需求；处理 HR 推送的业务筛选；参加一面、二面并填写反馈 |
| 招聘专员 | 接收需求、收取简历、HR 筛选、推送业务筛选、安排面试、根据反馈推进流程 |
| 招聘主管 | 查看和管理团队招聘需求、流程、面试与 Offer |
| 人力资源总监 | 查看全局招聘进展并处理需要总监确认的事项 |
| 系统管理员 | 管理账号、权限和系统配置，不代替 HR 推进招聘流程 |

本地验收也使用不同的真实账号重新登录，不在一个账号里假切角色。HR 推送后，任务写入数据库并出现在被指派的业务负责人/面试官账号中；其他面试官看不到。

## 3. 九阶段真实落点

| 环节 | 真实入口 | 主要操作者 | 服务端事实 | 外部状态 |
|---|---|---|---|---|
| 1. 需求生效 | `/jobs` | 招聘专员、经理 | Demand、Job、负责人、HC、审批/状态历史 | OA 自动承接待接入，可在站内创建和审核 |
| 2. 导入并解析简历 | `/jobs` 当前需求候选人抽屉；`/candidates` | 招聘专员 | 上传批次、候选人、原始文件、结构化解析结果、当前 Demand 关联 | 外部邮箱/渠道自动收件待接入 |
| 3. HR 初筛并推送 | 当前需求候选人抽屉；`/candidates` | 招聘专员 | Demand Flow、Pipeline 阶段、业务筛选任务和站内通知 | 企业微信任务卡待接入 |
| 4. 业务筛选 | `/interviewer/screening` | 被指派业务负责人/面试官 | 筛选决定、备注、处理人、处理时间 | 企业微信内直接操作待接入 |
| 5. 线下协调 | 系统外 | 招聘专员、候选人、面试官 | 系统仅保存后续确认的时间/地点/方式，不伪造沟通成功 | 电话、微信、现场沟通属于系统外 |
| 6. 创建面试 | `/interviews` | 招聘专员、经理 | Assignment、轮次、主/辅面试官、时间、地点、站内通知 | 企业微信日历/外部日历待接入 |
| 7. 面试评价 | `/interviewer/interviews` | 被分配面试官 | Feedback、评价结果、备注、提交/修改记录 | 企业微信提醒与回传待接入 |
| 8. 招聘专员决策 | `/interviews` | 招聘专员、经理 | 下一轮/加面安排，或 Pipeline 进入 Offer/带原因淘汰 | 无外部依赖 |
| 9. Offer 与入职 | `/offers` | 招聘专员维护、经理查看 | Offer 阶段、已完成面试轮数、OA 编号、OA 状态、登记人和时间；旧 Offer 记录继续兼容 | OA 自动发起/同步、邮件/短信、候选人自助接受待接入 |

旧 `/dashboard/interviews` 和 `/dashboard/offers` 只做跳转，分别收口到 `/interviews` 和 `/offers`，避免两套页面展示两套状态。

## 4. 招聘需求

业务负责人从公司模板创建需求。前端至少需要以下真实字段：

| 字段 | 说明 |
|---|---|
| `template_id` | 使用的公司招聘需求模板 |
| `job_title` | 岗位名称 |
| `department` | 用人部门 |
| `city` | 工作城市 |
| `headcount` | 招聘人数 |
| `business_owner_id` | 业务负责人账号 |
| `desired_onboard_date` | 期望到岗日期 |
| `priority` | 普通、紧急 |
| `responsibilities` | 岗位职责 |
| `requirements` | 任职要求 |
| `jd_text` | 完整岗位 JD |
| `focus_points` | 一面、二面需要考察的重点 |

业务提交后进入 HR 待确认状态。研发需要保留模板版本，避免模板修改后历史需求内容跟着变化。

## 5. HR 筛选与业务筛选

HR 在当前需求内可以直接筛选公司候选人，也可以把新简历拖入当前需求；简历库不是必经中转站。筛选支持城市、学历、技能、来源、当前阶段、流程状态、最低技能分、操作状态、排序和服务端分页。岗位没有配置技能时显示“匹配度未知”，不能显示假 0 分。

简历库把“简历求职目标”和“当前/最近招聘需求”分开显示：前者来自原始简历解析，后者来自系统流程关联，不能互相替代。PDF、DOCX 和图片沿用现有视觉模型进行文字识别和结构化抽取；解析不到的求职目标保持空白，不编造内容。

简历导入前后都执行强重复校验：原文件内容完全一致，或解析后的完整手机号/邮箱与当前组织活动候选人一致时，本次导入失败且不创建第二份档案。页面明确显示已有重复简历、匹配依据和有权限时的已有候选人入口；仅姓名相同不能直接拦截，批量导入允许部分成功。

当 Demand 可用 HC 为 0 时，历史候选人、流程和结果仍可查看，但系统禁止新加入、重新启用和跨需求转入，并明确提示先调整 HC 或确认完成需求。

HR 确认人选后选择业务负责人并点击“推送业务筛选”。候选人尚未关联需求时，入口写明“选择招聘需求并推送业务筛选”，避免误以为存在一个未显示的“当前需求”。只有待筛选、AI 初筛或业务筛选阶段允许推送；已进入面试、Offer、入职、淘汰或转出的候选人不得倒退。业务负责人看到：

- 候选人结构化简历信息：求职目标、个人概况、教育经历、工作经历、项目经历、技能、证书与语言、基本信息；不展示内部解析键或原始 JSON。
- 原版简历：PDF、Word 或图片的原始文件预览；有权限时可下载。
- 当前招聘需求和完整岗位 JD。
- HR 的筛选备注、推送人、推送时间和处理截止时间。

业务筛选固定三个结果：

| 结果 | 后续状态 | 备注要求 |
|---|---|---|
| 通过，进入一面 | 等待 HR 安排一面 | 可选 |
| 不合适 | 返回 HR，由 HR 确认淘汰 | 必填 |
| 需要 HR 补充信息 | 返回 HR 补充后再次推送 | 必填 |

业务负责人的筛选结果不自动淘汰候选人，也不自动创建面试；正式流程动作由 HR 执行。

## 6. 一面、二面与评价

HR 根据业务负责人可用时间安排一面或二面。每一轮是独立任务，必须保存轮次、面试官、时间和反馈，不能用后一轮覆盖前一轮。

- 安排或改约时间必须晚于当前时间，同一面试官的一小时占用窗口不能冲突。
- 面试尚未开始时，HR 和面试官都不能确认完成或提前评价；时间到达后，HR 或该任务所属面试官可“确认已面试”，确认后立即进入“待反馈”。
- 业务筛选已通过但未安排时显示“安排面试”；已有有效安排时显示“查看/调整面试”。
- 反馈回传后，HR 明确选择下一轮、增加面试官、进入 Offer 或带原因淘汰；系统不替 HR 猜下一步。
- HR 安排二面或后续轮次给不同账号后，新面试官始终可只读看到本人当前轮及此前轮次的完整评价，不会看到后续轮次，且始终不能编辑此前面试官的反馈；无关面试官不能读取该候选人历程。
- 面试通知携带具体任务编号；旧通知没有编号时打开该候选人的最新轮次，避免二面误开一面。进入 Offer 后可从历史面试直达对应 Offer；淘汰后仍显示原因和人才库去向。

面试详情需要同时展示岗位 JD、JD 中配置的考察重点、候选人信息、原版简历和之前轮次的反馈。

候选人和面试详情统一拆为“面试信息 / 候选人简历 / 面试评价”三个页签，底部始终显示任务状态和当前可执行动作；页签切换不重复读取接口，读取失败可在抽屉内重新加载。面试官详情只显示本人当前轮及此前轮次的完整评价，不展示未来轮次、Offer 薪资、HR 审批人员、业务筛选备注、淘汰信息或后续流程。列表页常用查询条件直接展示，状态颜色和主次操作按钮使用统一规则。

每轮面试评价使用结构化版本：

- 满意程度：`满意`、`待定`、`不满意`。
- 岗位匹配：`高匹配`、`基本匹配`、`低匹配`。
- 建议结论：`进入下一轮`、`建议进入 Offer`、`暂缓`、`不建议继续`。
- 优势、顾虑、补充备注分别填写，单项最多 1000 字；满意时优势必填，不满意时顾虑必填，待定时补充备注必填。
- 评价关联当前候选人、招聘需求、面试轮次和面试官。
- 提交后不可静默覆盖；修改必须保留修改时间和操作者。
- 面试反馈不自动推进、不自动淘汰、不自动进入 Offer，由 HR 查看后决定下一步。
- 面试官工作台只在本地按真实任务计算“待评价、超时待确认、两小时内开始”，不会因为刷新重复写通知；点击提醒直达具体任务。
- 一面、二面、终面固定对应第 1、2、3 轮，页面不可手填冲突数字，后端也会拒绝矛盾组合。
- 招聘专员从工作台进入待安排面试时，只有一条任务直接打开安排窗口；多条仍显示列表，零条显示明确空状态。
- 候选人列表可显示“相同文件 N 条”和“同名 N 条”只读提示；同名不代表同一人，任何提示都不能自动合并或删除。隐藏本地演示数据只影响当前页显示，可随时恢复。
- 工作台只把当前账号真正可处理的在招事项列为待办：需求待审核只给招聘主管/Admin；经理退回的 Offer 回到招聘专员待办；已关闭、暂停或已完成需求的旧任务不再占通知角标，但通知历史仍可按接口查询。
- 站内通知链接携带具体需求、候选人和任务编号；前端补充 `from=notification`，用户从通知进入后可以辨认来源，不会落到无筛选的普通列表。

## 7. 研发接口责任

用户无需提供接口文档。以下接口路径、鉴权方式、错误码和真实返回结构由研发负责提供，前端按本节业务语义对接：

| 能力 | 前端需要的动作 |
|---|---|
| 招聘需求模板 | 获取模板列表和模板详情 |
| 招聘需求 | 创建、查看、修改、审核/生效、关闭、恢复、查看 HC |
| 简历与候选人 | 上传、解析结果、候选人列表、结构化详情、原版简历预览/下载 |
| HR 筛选 | 在当前需求内筛选/导入候选人，查看匹配准备度，保存结论和备注，推送给指定业务负责人 |
| 业务筛选任务 | 获取本人待办；提交通过、不合适、需要补充信息 |
| 面试 | 安排一面/二面、确认、改约、取消、冲突校验、查询本人任务 |
| 面试反馈 | 提交满意程度和备注；读取历史轮次；受控修改 |
| 流程 | HR 推进、退回、淘汰和进入 Offer；读取完整历史 |
| Offer 与入职 | 招聘专员创建/修改草稿并提交；经理/Admin 确认或退回，不能由招聘专员自审；退回后招聘专员修改重提；记录发放、接受/拒绝、撤回/过期和实际入职；接受后锁定名额，只有实际入职计入已入职 HC |

所有写接口需要防重复提交，并返回可追踪的业务记录 ID。前端需要明确处理加载中、真实空数据、失败重试、401 登录失效、403 无权限和 409 状态冲突。

## 8. 研发验收场景

1. 业务负责人用模板创建需求，HR 能看到完整内容。
2. HR 在当前需求页面筛选已有候选人或上传一份真实测试简历，不跳转简历库也能完成 HR 筛选。
3. HR 推送给指定业务负责人，其他业务账号看不到该任务。
4. 业务负责人能同时查看结构化信息和原版简历。
5. 三种业务筛选结果都能保存，拒绝和补充信息缺少备注时不能提交。
6. 业务筛选通过后由 HR 安排一面；重复进入时显示查看/调整，过去时间和冲突时间不能保存。
7. 一面、二面分别保存满意程度和备注，历史反馈不被覆盖。
8. 面试官提交反馈后，HR 能立即看到结果并决定下一轮、加面、带原因淘汰或进入 Offer。
9. Offer 必须经历草稿、经理确认、记录发放和候选人答复；经理退回与候选人拒绝是两个状态，退回可修改重提且保留版本与意见。接受时锁定可用名额但不计入已入职 HC，撤回后释放，确认实际入职后只增加一次。
10. 刷新页面、退出并重新登录后所有记录仍存在，重复点击不会生成重复任务。
11. 未来面试评价、后续阶段退回业务筛选、未填淘汰/拒绝原因、越权访问分别得到明确的中文提示和 400/403/409。
12. AI 助手、BOSS 自动化和 KPI 标准不出现在试点导航。
13. 同一简历再次上传、完整手机号或邮箱重复时不产生第二份候选人；同名但联系方式不同的两人都能正常导入。
14. 一面通过后由 HR 安排不同账号负责二面；二面账号始终可只读查看同一需求的一面完整评价，但不能修改，一面和无关账号都看不到不属于自己的新任务或未来轮次。

## 9. 外部集成边界

当前内部闭环不等待外部系统，但必须如实展示状态：

- 站内任务和通知可以写“已创建”；企业微信任务卡只能写“待接入”。
- 站内面试日程可以写“已创建”；企业微信/外部日历只能写“待接入”。
- Offer 页面使用“记录为已发放”，不能写“邮件已发送”；候选人接受、拒绝由 HR 根据线下事实登记。
- OA 自动创建需求、企业微信身份映射、邮件、短信和候选人自助入口接入后，复用现有 Demand、Task、Assignment、Feedback 和 Offer 记录，不另建平行流程。

## 10. 暂不要求用户提供

- 公司接口文档。
- 数据库、服务器、域名和生产密钥。
- AI、BOSS 和 KPI 的接口定义。

这些内容由研发和 IT 在外部接口接入、SIT 和上线阶段补齐；缺少它们不允许页面伪造“已发送/已同步”，但不阻塞本地站内流程验收。
