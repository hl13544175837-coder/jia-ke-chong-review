# 5190 真实可用与上线改造矩阵

> 盘点日期：2026-07-26
>
> 开发起点：`codex/readdy-resume-ui-merge` 分支 `f48e433`；准确功能提交以 `git log -1` 为准
>
> 适用入口：`readdy-frontend`，本地端口 `5190`
>
> 目的：说明 5190 从“完整可点击演示产品”变成“真实业务系统”还缺什么。本文是开发排序依据，不代表已经上线。

## 1. 一句话结论

5190 的登录、公司权限菜单、招聘需求、候选人库和 Offer 已接入真实后端。创建需求的招聘负责人由后端按角色裁剪；候选人筛选在数据库分页前执行；Offer 在真实生命周期数据上提供列筛选。其余模块仍按本矩阵逐项清理 mock 和浏览器内存状态，不重写后端，也不牺牲 5190 的现有界面。

## 2. 当前代码事实

- 5190 路由配置共有 27 条路径声明（包含根跳转、登录、面试别名、角色页面和 404）。
- `readdy-frontend/src/features` 已为 Demand、候选人和 Offer 建立类型化 API 与业务类型；页面不再自行拼接这些模块的请求协议。
- 招聘需求的列表和写操作、简历上传与候选人库、Offer 列表和生命周期操作均读取真实后端数据。
- 候选人库支持搜索、学历、意向城市、技能、来源、解析状态、入流程状态、阶段和最低技能分筛选；筛选条件随请求传到服务端，并在分页前执行。
- 创建需求的招聘负责人选项来自后端权限结果；招聘专员只有本人一个合法选项时自动选中，但下拉仍可正常操作。
- `readdy-frontend/src/mocks/*` 仍服务于尚未真实化的页面，不能把已接线模块的完成状态外推为全站完成。
- 现有 Flask 后端已经提供 Demand、候选人、简历、流程、面试、Offer、BI、人才地图、KPI、通知、AI 会话、账号和审计接口。
- 5192 的 `frontend/src/lib/api.ts` 已提供类型化调用，可作为 5190 接线参考。

### 已发现的明确问题

1. 5190 的 AI 助手仍需以真实会话、失败重试和服务端权限作为正式验收依据，不能用固定答案或前端状态冒充成功。
2. 5190 的系统设置仍需逐项确认真实数据源；没有正式 API 的配置应保持只读或暂不开放。
3. 5190 在公司 profile 没有正式业务角色时会使用 `VITE_DEFAULT_ROLE=admin` 兜底。它可以联调，但不能作为正式 RBAC 结论。
4. 当前本地服务能运行不等于公司业务网关、公司数据库、LLM、视觉模型和生产环境已经可用。
5. 五套产品角色界面和菜单边界已恢复；人力资源总监目前只有本地产品视角，正式上线前仍需公司权限系统提供唯一身份映射和后端数据权限。

## 4. 可直接复用与真正缺失的边界

### 可以直接复用

- `frontend/src/lib/api.ts`：真实业务请求、Token、错误处理和主要数据类型。
- `frontend/src/pages/*`：5192 已经跑通的 Demand、简历、Kanban、面试、Offer、人才地图、KPI、BI、AI 和管理逻辑。
- `backend/app/api/*`：现有 Flask API。
- `backend/tests/*` 与 `frontend/tests/*`：权限、组织隔离、Demand、流程、面试、Offer、审计和部署门禁。

复用的含义是提取接口层和业务状态处理，不是把 5192 页面整页覆盖到 5190。5190 的页面结构、按钮、筛选、弹窗和角色工作台必须保留。

### 仍需补齐或由公司确认

- 公司网关是否已经部署可访问的 `/zhipin-server/api`。
- 公司身份如何稳定映射到 `admin / manager / recruiter / interviewer`，不能长期依赖默认 admin。
- 部门和通用系统配置的正式数据源及维护责任人。
- 企业微信/日历、邮件、短信等真实通知渠道是否纳入一期。
- 真实数据库类型、公司域名、HTTPS 证书、日志平台、备份位置和发布流水线。
- 简历发送给外部 LLM/视觉模型的合规结论、供应商、密钥和费用上限。
- 真实试点组织、管理员和四角色验收账号。

## 5. 推荐实施顺序

### 阶段 A：真实招聘最小闭环

1. 统一 5190 的 API 客户端、鉴权头、错误处理和数据类型。
2. 接招聘需求（Demand/Job）。
3. 接简历上传、解析和候选人库。
4. 接 Demand 看板和候选人流程流转。
5. 接面试安排、面试官任务和反馈。
6. 接 Offer 和已入职。

完成标准：从创建一条真实 Demand 开始，能够上传一份简历、加入该 Demand、推进阶段、安排面试、提交反馈、生成并完成 Offer；刷新浏览器后数据仍存在，换账号后权限正确。

### 阶段 B：管理和效率能力

1. 工作台和通知。
2. KPI 标准、Analytics 和总监页面。
3. 人才地图。
4. AI 助手和图片识别生产配置。
5. 管理员账号、审计和可开放的系统设置。

### 阶段 C：生产上线门禁

1. 生产密钥、严格 CORS、关闭调试和公开注册。
2. MySQL/PostgreSQL、Alembic 迁移、备份与恢复演练。
3. 公司域名、HTTPS、网关、日志、监控和告警。
4. 清理演示数据，建立真实试点账号。
5. 自动化门禁、四角色真人冒烟、组织隔离负向测试。
6. Libra/SIT 构建部署、镜像和提交一致性、回滚演练。

## 6. 每个模块的统一完成标准

模块只有同时满足以下条件才算“真实可用”：

- 页面不再从 `readdy-frontend/src/mocks` 读取该模块的业务事实。
- 所有写操作刷新后仍存在，重复点击不会生成重复记录。
- 加载、真实空数据、失败、重试、无权限和会话过期状态齐全。
- 前端路由、菜单/按钮权限、后端 RBAC 和组织隔离一致。
- 招聘事实明确归属 `demand_id`，不能只按 Job 或中文名称猜关联。
- 关键写操作有原因、审计记录和可恢复路径。
- 对应单元测试、接口测试、类型检查、构建和 Tabbit 真人主流程通过。

角色界面修复切片已于 2026-07-24 完成本地验收：恢复五角色产品模型；系统管理员、招聘主管、人力资源总监和面试官不再共用菜单；本地角色预览受开发环境和显式开关双重限制；Tabbit 已逐角色检查菜单与首页跳转。该切片只恢复产品视角，生产人力资源总监身份和后端数据范围仍是 P0。

本地身份映射于 2026-07-26 补齐：OAuth 验收桥的 profile 在工号之外透传后端真实数字 `userId`，5190 会话不再将 `hr01` 等工号强制转为数字。本地 `hr01` 重新登录后已在 Tabbit 创建需求 ID `6`，后端确认 `owner_hr_id=3`。正式公司网关仍需与业务后端提供稳定的同一人身份映射，不得从工号字符串推测用户 ID。

候选人库、招聘负责人和 Offer 筛选切片于 2026-07-26 基于 `f48e433` 完成：5190 的候选人多维条件进入真实分页查询，关键表头可直接展开筛选；招聘负责人下拉统一使用后端授权选项；Offer 在真实数据上提供五组列筛选和一键重置。旧版 `frontend/src` 未作为本轮实现入口。

后续切片继续按矩阵处理尚未真实化的页面，并在公司网关四角色环境补现场验收；不得因为上述三个模块通过而宣称全站已经达到生产上线标准。
