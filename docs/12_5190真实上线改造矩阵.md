## 1. 一句话结论

5190 的内部招聘主线已经统一到真实后端：需求内选人/上传、业务筛选、面试安排与评价、HR 后续决策、Offer 审批跟进和确认入职使用同一套 `demand_id` 数据。页面刷新和重新登录后读取数据库事实，不再依赖本地假角色或并行的旧面试/Offer 页面。OA、企业微信、邮件、短信、候选人触达和公司生产部署仍未接入，不能把本地闭环等同于生产上线。

## 2. 当前代码事实

- 5190 路由配置共有 27 条路径声明（包含根跳转、登录、面试别名、角色页面和 404）。
- `readdy-frontend/src/features` 已为 Demand、候选人、业务筛选、面试、Offer 和工作台建立类型化 API 与业务类型；核心页面不再自行维护平行业务事实。
- 招聘需求、需求候选人工作台、简历上传与候选人库、业务筛选、面试、工作台、Offer 和 HC 均读取真实后端数据。
- 候选人库支持搜索、学历、意向城市、来源、解析状态、精确流程状态、阶段和入库起止日期筛选；筛选条件随请求传到服务端，并在分页前执行。主列表本期隐藏核心技能、技能关键词和最低技能分入口，已有技能接口能力保留供二期恢复。
- 简历上传时 Demand 为选填；候选人可先沉淀到公司人才库，再预览岗位匹配后单人或批量进入流程。已淘汰候选人回到人才库并可带原因重新启用。
- 收藏按用户隔离；manager/admin 可按完整手机号或邮箱查重，只有无业务历史的重复档案可自动并入主档，流程、面试和 Offer 历史不会静默搬迁。
- 创建需求的招聘负责人选项来自后端权限结果；招聘专员只有本人一个合法选项时自动选中，但下拉仍可正常操作。
- 需求候选人工作台支持服务端分页、城市、学历、技能、来源、阶段、流程状态、最低技能分、操作状态和排序，并可直接预览/下载简历或拖入当前需求。
- 业务筛选、面试和 Offer 的阶段变化由后端状态机负责；未来面试、时间冲突、阶段倒退、越权和缺少必填原因均由后端拦截。
- 招聘专员、业务筛选人和面试官共用中文结构化简历展示；不直接显示 JSON、解析字段名或内部路径。
- `readdy-frontend/src/mocks/*` 可能仍服务于非试点页面；不能把内部招聘闭环的完成状态外推为全站所有管理增强和生产集成均完成。
- 现有 Flask 后端已经提供 Demand、候选人、简历、流程、面试、Offer、BI、人才地图、KPI、通知、AI 会话、账号和审计接口。
- 旧 `frontend/`（曾作为 5192 接口版）已从当前代码树删除，不再作为实现或验收入口；需要追溯时只看 Git 历史。

### 已发现的明确问题

1. OA 需求来源、企业微信任务卡和日历、邮件、短信、候选人自助答复尚未接入；当前只保存站内任务和 HR 的事实登记。
2. 公司 profile 到 `admin / manager / recruiter / interviewer / hr_director` 的正式唯一映射仍需公司环境确认；本地验收使用不同账号，不允许假切角色冒充权限通过。
3. AI 助手、系统设置、总监增强页等非试点模块仍需逐项确认真实数据源；没有正式 API 的能力应只读或不开放。
4. 当前本地服务能运行不等于公司业务网关、公司数据库、LLM、视觉模型、备份恢复和生产环境已经可用。
5. 人力资源总监已有独立后端代码角色 `hr_director`；正式上线前仍需公司权限系统确认人员身份和数据范围，不能只靠前端菜单名称。

## 4. 可直接复用与真正缺失的边界

### 可以直接复用

- `readdy-frontend/src/features/*`：真实业务请求、Token、错误处理和主要数据类型。
- `readdy-frontend/src/pages/*`：当前 5190 的页面、流程和角色入口。
- `backend/app/api/*`：现有 Flask API。
- `backend/tests/*` 与 `readdy-frontend/tests/*`：权限、组织隔离、Demand、流程、面试、Offer、审计和部署门禁。

复用的含义是提取接口层和业务状态处理，不是把 5192 页面整页覆盖到 5190。5190 的页面结构、按钮、筛选、弹窗和角色工作台必须保留。

### 仍需补齐或由公司确认

- 公司网关是否已经部署可访问的 `/zhipin-server/api`。
- 公司身份如何稳定映射到 `admin / manager / recruiter / interviewer / hr_director`，不能长期依赖默认 admin。
- 部门和通用系统配置的正式数据源及维护责任人。
- 企业微信/日历、邮件、短信等真实通知渠道是否纳入一期。
- 真实数据库类型、公司域名、HTTPS 证书、日志平台、备份位置和发布流水线。
- 简历发送给外部 LLM/视觉模型的合规结论、供应商、密钥和费用上限。
- 真实试点组织、管理员和五角色验收账号。

## 5. 推荐实施顺序

### 阶段 A：真实招聘最小闭环

1. 统一 5190 的 API 客户端、鉴权头、错误处理和数据类型。
2. 接招聘需求（Demand/Job）。
3. 接简历上传、解析和候选人库。
4. 接 Demand 看板和候选人流程流转。
5. 接面试安排、面试官任务和反馈。
6. 接 Offer 和已入职。

完成标准：从创建一条真实 Demand 开始，能够上传一份简历、加入该 Demand、推进阶段、安排面试、提交反馈、生成并完成 Offer；刷新浏览器后数据仍存在，换账号后权限正确。

### 阶段 B：管理和效率能力

1. 工作台和通知。
2. KPI 标准、Analytics 和总监页面。
3. 人才地图。
4. AI 助手和图片识别生产配置。
5. 管理员账号、审计和可开放的系统设置。

### 阶段 C：生产上线门禁

1. 生产密钥、严格 CORS、关闭调试和公开注册。
2. MySQL/PostgreSQL、Alembic 迁移、备份与恢复演练。
3. 公司域名、HTTPS、网关、日志、监控和告警。
4. 清理演示数据，建立真实试点账号。
5. 自动化门禁、五角色真人冒烟、组织隔离负向测试。
6. Libra/SIT 构建部署、镜像和提交一致性、回滚演练。

## 6. 每个模块的统一完成标准

模块只有同时满足以下条件才算“真实可用”。本轮负责人明确保留 Mock，因此含 Mock 的非试点模块不按此标准宣布完成，也不会阻断本地 Test/SIT 发布候选收口：

- 页面不再从 `readdy-frontend/src/mocks` 读取该模块的业务事实。
- 所有写操作刷新后仍存在，重复点击不会生成重复记录。
- 加载、真实空数据、失败、重试、无权限和会话过期状态齐全。
- 前端路由、菜单/按钮权限、后端 RBAC 和组织隔离一致。
- 招聘事实明确归属 `demand_id`，不能只按 Job 或中文名称猜关联。
- 关键写操作有原因、审计记录和可恢复路径。
- 对应单元测试、接口测试、类型检查、构建和 Tabbit 真人主流程通过。
