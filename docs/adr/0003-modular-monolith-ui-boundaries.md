# ADR-0003：采用模块化单体并锁定前端业务边界

## 状态

Accepted

## 背景

当前系统由一个 React 前端和一个 Flask 后端组成，适合内部招聘产品的小团队快速迭代。但候选人工作台已经增长到 2420 行，多个详情抽屉独立实现，仓库还保留不可达旧页面和运行时 Mock。继续按页面临时拼接会让一次改动影响多个功能板块，也会让自动测试验证到旧代码。

本轮目标不是新增业务能力，而是在不改变已审批流程和视觉的前提下，让候选人、需求、面试、Offer、人才地图可以分别修改和验证。

## 决定

1. 保持 React + Flask 的模块化单体，不拆微服务。
2. `src/pages` 只负责路由页面组合，不能引用其他页面目录的内部组件。
3. 可复用业务逻辑放入 `src/features/<domain>`；所有 `features` 禁止反向引用 `pages`。
4. 跨业务模块只能调用对方公开的 API、类型或公开组件，不能读取对方页面状态。
5. 正式路由可到达页面不得运行时读取 `src/mocks` 的业务事实；静态地区选项和纯类型必须迁移到明确的常量或类型模块。
6. 详情抽屉的遮罩、焦点、Escape、背景锁定、滚动和固定底栏由公共外壳统一管理。
7. 已知技术债先进入带路径的临时白名单，门禁禁止新增；对应整改完成时必须删除白名单。
8. 重构采用测试先行、小提交和逐入口浏览器验证，不整体重写。

## 影响

### 正面影响

- 修改一个业务模块时，影响范围可以通过目录边界和独立测试判断。
- AI/Codex 的任务可以明确限制到具体模块，减少改错文件。
- 已知 Mock 和大文件不会继续增长，并能按计划逐项归零。
- 现有单体部署和调试方式不变，不增加分布式系统成本。

### 负面影响

- 前期需要先补测试和搬移代码，短期功能开发速度会下降。
- 单体仍然整体构建和部署，不能像微服务一样独立发布单个模块。
- 临时白名单需要严格维护，否则可能被误当作永久例外。

### 中性影响

- 数据库和现有 HTTP 接口保持不变。
- 用户已审批的业务流程和视觉不因本 ADR 改变。

## 备选方案

### 直接拆微服务

不采用。当前团队和部署规模不需要额外的服务发现、网络调用、分布式事务和独立运维成本。

### 整体重写前端

不采用。一次性重写难以证明所有历史业务细节、角色权限和交互都被保留。

### 继续维持大页面，只补注释

不采用。注释不能建立编译或测试边界，也不能防止跨模块回归。
