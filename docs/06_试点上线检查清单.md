# 06 · 试点上线检查清单（v0.1-internal → 公司服务器小范围试点）

> 版本：2026-07-11 ｜ 状态：demand-scoped P0 代码候选的试点清单，环境门禁待执行
> 目标：把当前 `v0.1-internal` 内测基线，安全地部署到公司服务器，供少数 HR 用**真实数据**小范围试点。
> 范围：配置加固、部署与已批准 `demand_id` 迁移门禁。本阶段不接 OA 自动流转，需求由 HR 手工录入。

> 本清单只用于真实 HR/候选人数据试点与 GA，必须显式设置 `ALLOW_INSECURE_SIT_STARTUP=false`。当前项目负责人单人、可丢弃数据的 CFPD `test`/SIT 已授权使用宽松 RC 配置；该环境不得导入真实个人信息，也不得用其结果宣称已通过生产安全验收。

> 当前 `demand_id` P0 已形成合并前代码候选；SIT 演示数据允许清空或重建。Git 推送、Libra 构建和 SIT 部署是不同状态，本清单针对真实数据试点的门禁未因此自动完成。

## 2. 逐项展开

### C1 · 生产密钥与环境变量 〔配置加固〕

**为什么**：现在 `backend/app/config.py` 里 `JWT_SECRET` 默认值是 `dev-secret-change-in-prod`、`SECRET_KEY` 默认 `dev-secret`。沿用默认值任何人都能伪造登录令牌，等于无认证。

**动作**：
1. 在服务器生成强随机密钥（不要写进代码、不要进 git）：
   ```bash
   python3 -c "import secrets; print(secrets.token_urlsafe(48))"
   ```
2. 写入 `backend/.env`（参考 DEPLOYMENT.md §3.3 的 `.env` 用法）：
   ```env
   FLASK_DEBUG=false
   LOCAL_SCHEMA_COMPAT=false
   JWT_SECRET=<上一步生成的强随机串>
   JWT_EXPIRY_HOURS=8
   UPLOAD_FOLDER=/var/lib/zhipin/uploads
   ```
3. 确认 `.env` 已在 `.gitignore` 中（项目已忽略，勿提交真实密钥）。

**验收**：`grep JWT_SECRET backend/.env` 不再是 `change-in-prod`；用旧 demo token 访问 `/api/jobs` 返回 401。

**红线核对**：只改环境变量取值，不改 `config.py` 读取逻辑、不改认证机制 → 符合 R5。

### C2 · CORS 收紧 〔配置加固〕

**为什么**：生产环境不能允许任意网站跨域调用接口。当前代码复用严格 origin 校验：除不能为空，还会拒绝 `*`、`null`、URL 用户名/密码、路径、query、fragment 和非 HTTP(S) scheme，配置错误时拒绝启动。

**动作**：在服务器 `backend/.env` 配置公司前端域名：
```env
CORS_ORIGINS=https://zhipin.内网域名
```
> 若采用 R2 的「Flask 同源托管 dist」方案，也必须配置实际访问域名，确保生产安全校验通过。

**验收**：`python3 backend/scripts/check_pilot_readiness.py` 的 CORS 检查通过；从非白名单域名发起的浏览器请求被拦截，同源页面正常。启动与运维日志只显示数据库 driver/host/database 的脱敏 label，不打印用户名、密码或 query。

**红线核对**：只改服务器 `.env`，不换中间件、不改路由 → 符合 R3 / R5。

### C3 · 数据库切 MySQL/PostgreSQL + 定时备份 〔部署〕

**为什么**：开发默认 SQLite（单文件、并发弱、易随容器重置丢失）。多人试点用真实简历，必须切到 DEPLOYMENT.md §6 已认可的 MySQL 或 PostgreSQL，并做备份。

**动作**：
1. 在公司服务器建 MySQL 或 PostgreSQL 库与账号。
2. `.env` 配置（DEPLOYMENT.md §6 方案 A 写法）：
   ```env
   DATABASE_URL=mysql+pymysql://user:pass@host:3306/zhipin?charset=utf8mb4
   ```
   > MySQL 使用 `mysql+pymysql://`；如使用 PostgreSQL，代码会自动把 `postgresql://` 转成 SQLAlchemy 的 `postgresql+psycopg://` 驱动形式。
3. 真正空库显式执行 `python backend/scripts/bootstrap_database.py --allow-empty`；脚本只接受空库并 stamp 当前 head，缺失任一 `20260710_01` 之前旧基线业务表的库会拒绝继续且不 stamp；`candidate_demand_flows` 由该 Expand revision 创建，不属于旧基线。已有库由唯一 migration job 执行 `cd backend && alembic upgrade head`；业务应用不建表。本代码候选期望 `alembic current` 为 `20260806_15`。
4. 配置每日备份：MySQL 使用 `mysqldump --single-transaction`，PostgreSQL 使用 `pg_dump`，保留至少 7 天。

**验收**：后端连上目标数据库启动无报错；`alembic current` 明确为 `20260806_15`；`mysqldump`/`pg_dump` 能导出；带 manifest/SHA-256 的数据库与 uploads 快照至少恢复到一个同引擎临时库/临时目录并完成关键表与原简历核对。revision 15 后的新原件还要验证数据库副本可预览。`/api/health` 只证明进程存活，不能替代 schema 或恢复证据。

**红线核对**：仅切换 SQLAlchemy 的引擎 URL，schema 不变、ORM 不变 → 符合 R4。

### C4 · HTTPS 〔部署〕

**为什么**：简历、候选人手机/邮箱属敏感个人信息，裸 HTTP 传输有泄露风险。公司内网最低也要 HTTPS。

**动作**（二选一，均不改应用代码）：
- **方案 A（推荐）**：Nginx 反向代理在前，挂公司证书，转发到 `127.0.0.1:5000`。
- **方案 B**：若已有公司统一网关/负载均衡终结 TLS，则后端只监听内网回环。

> Cloudflare 免费隧道（DEPLOYMENT.md §7）仅适合临时演示，链接会变，**不用于正式试点**。

**验收**：浏览器访问为 `https://`，证书有效；HTTP 自动跳转 HTTPS。

**红线核对**：TLS 在应用之外终结，部署仍是「一个 Flask + 一个前端」 → 符合 R2。

仓库已提供 Nginx 样例：

```bash
deploy/nginx/zhipin.conf.example
```

使用前替换域名和证书路径，再把后端转发到 `127.0.0.1:5000`。

### C5 · LLM Key 配置 + 数据外发合规确认 〔合规〕

**为什么**：简历解析、JD 结构化、AI 面试、AI 助手都会把内容发给外部 LLM（DeepSeek/OpenAI）。真实简历含个人信息，**外发前必须经公司确认合规**——这是上线最关键的非技术卡点。

**动作**：
1. **先确认合规**：向公司法务/IT 确认「能否把候选人简历内容发送给外部 LLM API」。若不允许，本次试点可先只用离线功能（候选人库/岗位/流程/BI 离线可用，见 DEPLOYMENT.md §5 表），AI 解析等暂缓。
2. 合规通过后，在 `.env` 配置生产 Key（沿用现有字段，不改调用代码）：
   ```env
   LLM_PROVIDER=deepseek
   LLM_API_URL=https://api.deepseek.com/v1/chat/completions
   OPENAI_API_KEY=<生产 key>
   AI_RECRUITMENT_COMPLIANCE_ACK=true
   CANDIDATE_PRIVACY_NOTICE_URL=https://zhipin.内网域名/privacy
   AI_HUMAN_REVIEW_REQUIRED=true
   ```
3. 设月度预算/调用上限，避免试点期间费用失控。

**验收**：合规结论有书面记录；上传一份真实简历能正常解析（或确认已走离线模式）。

**红线核对**：沿用既有 DeepSeek/LangGraph 路线与 `.env` 字段，不换模型框架 → 符合 R3。

### C6 · 清演示数据、删 demo 账号、建真账号 〔数据〕

**为什么**：种子数据用于 MVP 内部试用；正式试点前应清理样例候选人，并用管理员创建真实试点账号。

**动作**：
1. 生产库**不要**运行 `seed_dev.py`（那是演示数据）。
2. 先预览清理范围：
   ```bash
   python backend/scripts/cleanup_demo_data.py --dry-run
   ```
3. 确认备份目录、数据库和上传目录无误后，再由负责人确认执行：
   ```bash
   python backend/scripts/cleanup_demo_data.py --confirm
   ```
   脚本会先生成标准可恢复快照，再删除 `@mvp.local` demo owner 以及包括 `candidate_demand_flows` 在内的关联业务事实；只删除这些事实独占引用的上传文件，真实 owner、无关文件和跨范围引用不会被顺带删除。检测到混合归属会 fail closed；schema 保留。MySQL `--confirm` 清理被禁止，必须走同引擎恢复演练和受审计的 DBA 方案。
4. 删除历史演示账号或临时试用账号。
5. 由 admin 在系统设置/用户管理中创建试点账号；登录页不开放自注册，只提示使用管理员分配账号。
6. 招聘专员尽量一人一个账号，以便系统区分 Demand/候选人当前责任与历史操作行为者；BI 不借此做个人排名或绩效结论。
7. 面试官账号只用于查看“我的面试”和填写反馈，不作为 HR 管理账号使用；不开放全量简历库、候选人流程和 AI 助手主入口，也不能直接推进 Offer 或淘汰。
8. 如试点用户忘记密码，由 admin 在用户管理中重置密码，再通过企业微信/线下安全方式发给本人。
9. 真实岗位/需求由试点 HR 在系统内**手工录入**（本阶段不接 OA）。
10. BOSS 直聘是实验辅助能力，不属于 HR 试点主流程必测项；但 `/api/boss/*` 路由已注册，测试/生产 `.env` 仍必须配置固定合法的 `FIELD_ENCRYPTION_KEY`，避免 Cookie 导入后无法加密或重启后无法解密。生成命令：`python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`。

**验收**：用户列表无历史演示账号；候选人库为空或仅含真实数据；旧演示密码无法登录；登录页无自注册入口；admin 可创建账号并重置密码；招聘专员登录后工作台只看当前 Demand 进度、瓶颈、责任协同和今日待办，不出现个人绩效或奖金结论，点击待办可直达对应 Demand/候选人流程阶段或面试待反馈列表；任一工作台分区接口失败时显示“数据暂不可用”和重试，KPI 不伪装成 0 或“暂无卡点”；面试官登录后左侧只看到工作台和“我的面试”主入口，任务卡可直接点击“填写反馈”，填写反馈时不出现“推进 Offer/淘汰”按钮；BOSS、OA 占位、职位模板顶级入口和无真实数据 BI 不出现在 P0 主导航（人才地图已被 2026-07-21 Readdy 迁移明确需求取代并进入正式主导航，以 `docs/11` 为准）；`python3 backend/scripts/check_pilot_readiness.py` 中 `FIELD_ENCRYPTION_KEY` 检查通过。

**红线核对**：仅数据层操作，不改 schema、不改 auth 逻辑 → 符合 R4 / R5。

### C7 · 自动化门禁全绿 + 真人冒烟 〔验收〕

**为什么**：上线前必须证明代码是绿的、流程是通的。当前固定门禁以本文列出的命令和 SDD 测试入口为准，不依赖已删除的历史计划。

**动作 1 — 自动化门禁**（在你本机/CI 跑）：
```bash
./scripts/check-sit-release.sh
```
> 统一门禁检查测试、类型、Lint、构建、前后端依赖安全、Alembic head、Git 敏感文件和 RC 镜像参数。它不会迁移数据库、清理数据、提交或发布。服务器真实 `.env` 仍须另外运行 `check_pilot_readiness.py`；小团队 Test 使用 `--profile sit-team`，真实数据试点使用默认严格 profile。

**动作 2 — 五角色真人冒烟**：管理员建账号 → 招聘专员用同一 Job 创建两个 Demand → 上传简历并从匹配加入具体 Demand → 验证兄弟 Demand 的看板/历史/Offer/HC 不串账 → 原子转需求并确认 `transferred` 不算淘汰 → 并发安排同轮两个 primary（一个成功、一个稳定 409、库中仅一条）并安排辅助面试官 → 同 assignment 并发重复反馈只保留一条 → 面试官从原始简历进入本轮反馈且反馈不自动推进 → 经理看 Demand 进度/卡点/当前责任且不出现个人排名 → 人力总监只读查看授权范围的管理分析 → 分区接口失败显示不可用/重试而非 0 → 管理员查 demand-indexed 审计 → 越权、空态和反向补救路径验证。

**验收**：门禁命令全绿（除允许的 warning）；10 步冒烟全部通过，越权路径确认被拦截。

**红线核对**：原样沿用既有门禁与冒烟脚本 → 符合 R6。

### C9 · 上线后观察项 〔运维〕

- 日志：确认 `logs/` 有应用日志，定期查错误。
- 备份：确认 C3 的每日备份真在跑，且能恢复。数据库和 `uploads/` 要一起备份。
- 回滚：保留上一可用版本（git tag `v0.1-internal` 已在），出问题能快速切回。
- 反馈：建一个试点 HR 反馈收集入口（群/文档），为 v0.2 与 OA 对接攒需求。

备份脚本：

```bash
cd backend
python scripts/backup_pilot_data.py --dry-run
python scripts/backup_pilot_data.py
```

建议用 cron 每天跑一次，`BACKUP_DIR` 指到服务器专门的备份目录。SQLite 备份使用 online backup API 保证 WAL 一致；所有快照必须有 manifest/SHA-256，目录和敏感文件权限分别为 `0700/0600`。

恢复演练不直接覆盖生产库，先恢复到临时库和临时目录。新快照的 manifest 会记录 `uploads.source_root`，恢复时将根内候选人附件路径转为安全相对路径；旧快照无该字段时只能同原根恢复。脚本会在 staging 校验 manifest、校验和和归档成员，拒绝路径穿越、链接和特殊文件，再原子切换 uploads；数据库与 uploads 不是跨资源事务，演练必须停写并分别核对，最后必须从应用实际读取一份原简历。必须先 `--dry-run`，确认目标库和上传目录无误后再 `--confirm`。MySQL 自动 `--confirm` 恢复会 fail closed，只能 dry-run 后由 DBA 在同引擎临时库执行并留证：

```bash
createdb zhipin_restore_check
DATABASE_URL=postgresql://user:pass@host:5432/zhipin_restore_check \
UPLOAD_FOLDER=/var/lib/zhipin/restore-check-uploads \
python scripts/restore_pilot_data.py --backup-path "$BACKUP_DIR/<backup-dir>" --dry-run

DATABASE_URL=postgresql://user:pass@host:5432/zhipin_restore_check \
UPLOAD_FOLDER=/var/lib/zhipin/restore-check-uploads \
python scripts/restore_pilot_data.py --backup-path "$BACKUP_DIR/<backup-dir>" --confirm
```

手工排障时也可以拆开验证，但正式演练优先用脚本，因为脚本会拒绝带路径穿越的 `uploads.tar.gz`：

```bash
tar -xzf "$BACKUP_DIR/<backup-dir>/uploads.tar.gz" -C /tmp/zhipin-upload-restore-check
```

验收完成后删除临时资源：

```bash
dropdb zhipin_restore_check
rm -rf /tmp/zhipin-upload-restore-check
```

### C11 · 用户可用性缺口检查 〔产品验收〕

**为什么**：自动化测试通过，只能说明主流程大体可运行；真实 HR 试用时更容易卡在“岗位没得选、候选人为空、面试官账号没建、岗位被关闭后找不到、推进错了不知道怎么改”这些边界场景。试点前必须把这些卡点提前点一遍，不能只按理想数据判断。

**动作**：

1. 用招聘专员账号检查：
   - 进入招聘需求页时，创建区是否默认收起，需求筛选和汇总表是否在首屏更易找到；点击“展开 / 收起”是否保留已填内容，提交期间是否禁止收起，失败时是否留在展开态显示错误。
   - 展开创建区后，职位 / JD 是否保持未选择，只有用户明确选中后才带出城市和部门；提需求日期是否为用户本地当天而不是 UTC 前一天。
   - 创建需求时，“默认面试官”是否可留空，能否按姓名/邮箱搜索；“例如：王杰”是否只是 placeholder，不会自动选人。选中后到面试安排选该 Demand，是否自动带出且仍可换人。
   - 在较长需求详情页底部分别打开暂停/关闭、恢复、优先级和转派弹窗，是否始终出现在当前视口；矮屏时内容是否可滚动、底部按钮是否仍可见。
   - Demand 操作成功但详情刷新失败时，是否明确提示页面可能仍为操作前状态、禁用重复动作并提供重试；负责人列表失败时是否只阻止转派且说明原因。
   - 两个同组织用户用空格/大小写变体或并发创建同一需求编号时，是否最多成功一条并返回可理解冲突提示。
   - 新建用人需求时，如果没有目标岗位，是否有清楚提示和“去新建岗位”的入口。
   - 工作台“今日待办”是否能直接进入业务待反馈、面试中、Offer 或待补反馈，而不是只进入普通列表首页。
   - 上传简历时是否只进入简历库；如果要推进某个招聘需求，是否能知道下一步去简历库选择具体“目标招聘需求”后加入对应流程。
   - 上传 PDF、DOCX、ZIP 是否正常；旧版 `.doc` 是否被跳过并提示宏风险；超大、伪装扩展名、损坏文件是否不会阻断其他文件。
   - 误导入一批简历时，是否能按上传批次撤回；撤回后候选人是否从列表、看板、匹配里消失，原文件是否删除，审计日志是否有撤回原因。
   - 工作台是否能快捷进入招聘岗位；招聘岗位列表里每个在招岗位是否能直接看到「匹配候选人」，且没有再多一层重复的选岗页面。
   - 岗位匹配页是否能在 AI 推荐之外切到“全部候选人”，按已知姓名、公司、学校、岗位、技能或邮箱人工补找，并只把当前筛选后勾选的人批量加入流程。
   - 简历库使用中文输入法搜索时，拼音组词期间是否不触发查询；查询期间页面和旧结果是否保持可见；无结果时“简历总量”是否仍为全库总数。
   - 候选人加入岗位流程时，如果候选人为空或岗位为空，是否有下一步入口；列表不为空但找不到目标项时，也要有“上传简历 / 新建岗位”的入口。
   - 候选人流程默认是否避开空阶段；用户手动点到空阶段时，页面是否提示去非空阶段、去匹配更多候选人或上传简历。
   - 候选人推进错阶段或淘汰错人时，是否能用“修正阶段”补救，并强制填写修正原因；时间线是否显示“阶段修正”。
   - 尝试打开别人负责岗位、把自己的候选人推进到别人岗位、或把候选人上传到已关闭岗位时，后端是否返回无权或岗位已关闭。
   - 同一面试官同一时间安排两场不同面试时是否被 409 拦截；同一 Demand/候选人/轮次并发安排两个 primary 时是否一个成功、一个稳定 409 且数据库仅一条；同一安排重复点击是否返回已有记录。
   - 面试官选项接口失败时，已有面试记录、待反馈任务和已分配任务是否仍可查看；新安排区是否单独提示失败、禁用保存并允许局部重试。
   - 误安排且尚未反馈时，Demand owner/经理/Admin 是否能填写原因取消、释放主面试官轮次槽并重新安排；已有反馈后是否稳定拒绝取消，已取消任务是否立即失去反馈入口。
   - 同一 assignment 并发重复提交反馈时是否复用已有反馈，数据库唯一索引是否阻止第二条。
2. 用招聘经理/负责人账号检查：
   - BI 是否能按 Demand 解释当前进度、停滞、待补反馈、HC、当前责任与下一步，所有数字是否可下钻；招聘专员响应只含当前 workload，不含绩效字段；请求失败必须显示不可用与重试，不得展示 0 或“暂无卡点”。
   - 岗位被关闭后是否还能找到历史数据，是否需要恢复岗位。
   - 同一 Job 的两个 Demand 不同负责人是否只能管理自己的 Demand；Job 模板维护人是否不会因此获得全部流程权限。
   - 候选人负责人是否能通过招聘专员下拉框转派，并要求填写转派原因，不要求输入用户 ID。
3. 用面试官账号检查：
   - 左侧菜单是否只保留面试官真正需要的入口。
   - 如果没有分配面试，空页面是否说明原因。
   - 有待反馈任务时，任务卡是否直接提供“填写反馈”，点击后是否定位到候选人和岗位对应的反馈表。
   - 即使知道候选人 ID、岗位 ID，也不能调用 AI 预筛、推进流程或提交关闭岗位的反馈。
   - 填写反馈后，HR/经理是否能看到反馈沉淀。
4. 用管理员账号检查：
   - 系统设置是否按“账号管理 / 审计日志 / AI 边界”分区；账号管理是否先展示成员列表，需要时再展开创建账号表单。
   - 能否创建账号、停用账号、调整角色、重置密码；角色/启停/密码变化后旧 token 是否立即 401，账号事实和审计是否同时成功或同时回滚。
   - 如果没有可选面试官，管理员是否能看到用户管理入口；非管理员是否能看到“联系管理员创建或启用面试官账号”。
   - 面试官账号停用后，是否不能继续被新安排面试；旧页面或旧请求是否被后端拦截。
   - 用户管理为空时是否提示先创建管理员、招聘专员和面试官，并提醒试点建议一人一个账号。
   - 当前是否需要“查看已关闭岗位 / 恢复岗位 / 限定试点岗位范围”的管理能力；暂不做的要列为已知限制。
   - 打开候选人详情、导出候选人 CSV、删除候选人、转派负责人、推进流程、关闭/恢复岗位后，审计日志是否能看到操作者、角色、目标、request_id、IP、来源、结果和失败原因。
   - 同一账号短时间连续导出候选人 CSV 后，管理员审计页是否把高频导出标红为告警。
   - 越权访问候选人详情或简历详情时，接口是否返回 403，审计日志是否出现 `security.forbidden` 并在管理员页面标红。
   - AI 工具目录是否只保留解析、匹配、总结和建议，不再暴露自动淘汰、推进、Offer、转派或关闭需求工具。
   - 管理员重置密码、用户自己修改密码后，旧 token 是否立刻 401；重新登录是否正常。
5. 用未登录用户检查：
   - 所有 `/api/*` 业务接口是否返回 401 或登录提示，不能看到候选人、岗位、反馈、文件路径、BI 或 AI 对话内容。
6. 用多组织数据检查：
   - 组织 A 用户通过修改 `candidate_id`、`job_id`、`interview_id`、`feedback_id`、`user_id` 是否仍不能访问组织 B 数据。
   - 组织 A 管理员是否只能看到本组织账号、审计日志、岗位、候选人和 BI。
   - 新组织开通是否已通过部署初始化写清 `org_id`、首个管理员和历史数据归属。

**验收**：招聘专员、招聘经理/负责人、面试官、管理员、未登录用户和多组织隔离各走一遍后，形成“可直接发给试点用户的问题说明”：哪些能用、哪些是已知限制、用户卡住时应该找谁。

### C12 · 逆向验收十角度检查 〔产品验收〕

**为什么**：正常成功路径只能证明“会用的人能走通”。试点更容易暴露的是点错、没数据、权限不一致、数字解释不清、部署版本不一致。每次说“全面测试”时，都按以下十个角度反向验收。

**动作**：

1. 反向路径：点错、选错、刷新、半路退出、数据为空、接口返回错误时，页面是否告诉用户下一步。
2. 不同角色：招聘专员、主管、面试官、管理员分别看得到什么、能改什么、不能越权做什么；AI 助手首页示例问题也要符合角色权限，不能把招聘专员引导到经理/管理员才有权限的团队 BI 或治理入口。
3. 数据闭环：上传简历、加入 Demand、推进、面试、Offer、入职后，候选人详情、Demand 看板、面试任务页、审计和 BI 是否使用同一 `demand_id`。
4. 脏数据：重复候选人、解析失败、来源别名、停用账号、关闭岗位、缺手机号/邮箱时是否有兜底。
5. BI 反查：每个数字能否追到 Demand、候选人、当前负责人、历史推进人、面试官和时间范围，且 `transferred` 不计淘汰。
6. 误操作恢复：关闭、淘汰、推进、转派、未反馈面试取消重排、停用账号、重置密码后，是否有补救或明确风险说明；已有反馈任务不得取消。
7. 下拉框目标缺失：完全没数据、有数据但没有目标、目标被关闭/停用三种情况都要测。
8. 重复点击/并发：同一按钮连点、重复上传、重复推进、重复安排和重复反馈是否复用已有结果；同轮 primary 由 `uq_interview_assignment_primary_slot` 最终兜底，同 assignment feedback 由 `uq_interview_feedback_assignment_id` 兜底；普通写接口同 `Idempotency-Key`/同请求体重试返回第一次结果，同 key 不同请求体 409。
9. 部署版本一致：本地代码、commit、tag、部署包、文档必须是同一版，避免本机有但服务器没有。
10. 非技术用户理解：页面不能要求用户理解技术字段；错误提示必须是业务语言，并说明找谁或去哪一步处理。

**验收**：输出 P0/P1/P2 清单。P0 是会阻断试点或造成权限/数据归属错误的问题；P1 是用户会卡住或主管解释不清的问题；P2 是体验优化或试点中可继续观察的问题。

### C13 · demand_id 迁移与回滚门禁 〔数据/发布〕

**为什么**：同一 Job 并行多个 Demand 后，旧 job-scoped 代码无法表达新事实。只发布镜像或只备份不恢复，都不是可接受的发布证明。

**动作**：

1. 在脱敏的同引擎克隆库运行 audit，得到零 Demand、唯一 Demand、多 Demand 可唯一映射、多 Demand 歧义、跨组织/孤儿数据分类。
2. 歧义数据必须由业务负责人批准映射；脚本不允许默认选最新/当前 Demand。
3. 运行 Expand migration 和 backfill dry-run；每条回填记录旧 ID、demand_id 和依据，且可幂等重跑。
   当前加性链为 `20260710_01` → `20260711_02` → `20260711_03` → `20260711_04` → `20260721_05` → `20260721_06` → `20260722_07` → `20260724_08` → `20260726_09` → `20260728_10` → `20260729_11` → `20260729_12` → `20260730_13` → `20260804_14` → `20260806_15`；11 新增简历 SHA-256 指纹和组织索引，12 新增简历版本留档，13 新增面试改约申请，14 新增本地 OA 结果登记字段和索引，15 新增当前和历史简历的数据库原件副本。任一 revision 发现无法安全决策的存量冲突都应中止，不自动挑选“赢家”。
4. verify 确认核心事实 `demand_id` 无空值、`job_id == demand.job_id`、每条旧记录恰好映射一次，歧义、孤儿和跨组织错配为 0。
5. 目标若为 MySQL，先用同一 `database.sql` 恢复到临时 MySQL 库并核对关键表；当前自动恢复未实现/未验收时，必须有 DBA 负责人与证据。
6. 在 SIT 部署 dual-write 兼容版，完成兄弟 Demand 隔离、旧 job-only 409、五角色 RBAC、AI 不写流程、BI 对账与旧 worker/旧资产退出检查。
7. 记录 cutover marker、CFPD SHA、Libra CommitID、schema revision、backfill/verify 报告、备份恢复证据、后端版本和前端资产哈希。

**回滚界限**：Expand/Backfill/Dual-write 且未产生并行 Demand 事实时，可回退兼容应用并保留加性 schema。一旦允许同 Job 并行多 Demand，不能只回退镜像；只能向前修复，或停写后恢复 cutover 前数据库 + uploads 整套快照，并接受 cutover 后数据丢失。

**验收**：上述每一项都有环境、commit/revision、负责人、时间和证据；缺任一项不设置 cutover marker，不开放真实用户。
